Customer Support Resolution Agent

A production Claude agent handles inbound support tickets, routes them by case type, resolves autonomously where possible, and escalates to human agents when criteria are met.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D2 MCP Tool Design2.1, 2.3Overlapping tools (get_customer vs lookup_order) with minimal descriptions cause misrouting
D4 Prompt Engineering4.1, 4.2Escalation miscalibration → explicit criteria + few-shot contrastive examples fix it
D5 Context Management5.2, 5.3, 5.5Long session fact preservation; escalation triggers; human review workflows
D1 Agentic Architecture1.4, 1.5Compliance gates for financial/identity operations via PreToolUse hooks
Key Concepts & Architectural Decisions
  • Tool descriptions are the primary routing mechanism — fix both overlapping tools, not just the one being misrouted
  • Escalation miscalibration = ambiguous decision boundary → fix with explicit criteria + few-shot contrastive examples (resolve vs. escalate side by side)
  • LLM self-reported confidence is poorly calibrated — never gate escalation on model confidence scores
  • Sentiment detects frustration, not case complexity — do not use sentiment as an escalation trigger
  • For financial/identity operations: PreToolUse hook enforces identity verification before downstream tools execute (prompt instructions have non-zero failure rate)
  • Transactional facts (order numbers, amounts, dates) → persistent case-facts block outside summarized history, not a revised summarization prompt
  • NEWValid escalation triggers are narrow: policy ambiguous/silent, repeated failed clarification with no progress, or an explicit human request (honor it immediately). An angry-but-solvable case with no explicit request should not escalate — acknowledge the emotion and offer resolution.
  • NEWContradictory stated preferences (e.g. "low risk tolerance" then a request for aggressive trades) call for structured preference tracking — surface the specific contradiction and ask which one governs. Neither "always escalate" nor "latest preference silently wins" is correct.
Exam Traps
⚠ Trap 1 — More instructions instead of examples
When escalation rates are miscalibrated, choosing "add more detailed instructions" instead of "add few-shot examples with contrastive cases" is wrong. Instructions fail at ambiguous boundaries. Examples show the model what the distinction looks like in real cases.
⚠ Trap 2 — Routing classifier before fixing descriptions (Q2)
Building an ML routing layer to pre-select tools over-engineers the problem and bypasses LLM natural language understanding. The correct first step is always enriching both tool descriptions with input formats, example queries, edge cases, and use-vs-similar-tool boundaries.
⚠ Trap 3 — Sentiment as escalation trigger (Q3)
A frustrated customer with a simple problem does not need escalation. A calm customer with a complex billing dispute does. Sentiment ≠ case complexity — they are independent signals.
⚠ NEWTrap 4 — Escalating a contradiction, or silently honoring the latest preference
Both "always escalate to a human" and "the most recent statement wins" are wrong. The correct move stays inside the agent: track preferences in a structured block, surface the contradiction, and ask which one governs.
✓ Clarifying Insight
This scenario almost always contains one tool-selection question and one escalation question. For tool selection: root cause = thin descriptions → fix both tools. For escalation: root cause = ambiguous criteria → add few-shot examples with contrastive cases. Neither is solved by ML classifiers, confidence scores, or sentiment analysis. NEWA third question type on recent mocks: preference contradictions, resolved via structured tracking + explicit surfacing — not escalation or silent overwrite.

Code Generation with Claude Code

Developers use Claude Code interactively to write, review, and refactor code — including large-scale multi-file architectural changes and custom review skills.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D3 Claude Code Workflows3.2, 3.4, 3.5context: fork for verbose skills; plan mode for architectural changes; CLAUDE.md rules
D1 Agentic Architecture1.3, 1.7Context isolation for verbose subagent output; independent review instances
D4 Prompt Engineering4.1Structured prompts for code review output consistency
Key Concepts & Architectural Decisions
  • context: fork in SKILL.md frontmatter: runs skill in isolated subagent — verbose intermediate output stays in the fork; only final summary returns to main session (Q4)
  • Plan mode first for multi-file architectural changes — explore codebase and understand dependencies before any implementation (Q5)
  • Independent review = separate Claude instance — same-session review is biased by the model's prior reasoning; it is less likely to challenge decisions it just made
  • CLAUDE.md rules and .claude/rules/ glob patterns enforce coding conventions automatically without developer invocation
  • NEWDelegation split for very differently-sized simultaneous requests: a large multi-file change (e.g. renaming a class used across 60 files) goes to a scoped subagent — direct handling risks attention dilution across that many files. A trivial single-file change is handled directly by the coordinator — delegation overhead isn't worth it. "Full codebase awareness means the coordinator should handle the rename itself" is a trap that inverts the rule.
  • NEWMultiple reported code issues where one is a shared dependency (e.g. an output-schema field name the other fixes must target): resolve the real dependency first, standalone, then sequence the remaining independent fixes one at a time. Don't batch everything into one message — batching independent fixes risks conflating which feedback applies to which fix.
Exam Traps
⚠ Trap 1 — model: haiku to reduce verbosity (Q4)
Not a valid SKILL.md frontmatter field. The correct mechanism to isolate verbose output is context: fork. A smaller model does not prevent intermediate output from polluting the main session context window.
⚠ Trap 2 — Start in execute mode, switch to plan mode if needed (Q5)
"Begin implementing and only switch to plan mode if complexity surprises you" is always wrong for tasks with architectural implications or changes across dozens of files. Plan mode first is the documented correct approach — not a fallback.
⚠ Trap 3 — Same-session self-review
The model retains reasoning context from generation, making it less likely to question its own decisions. A second Claude instance reviewing only the final artifact catches what the first won't. The exam guide explicitly calls same-session self-review an anti-pattern.
⚠ NEWTrap 4 — Coordinator handles the large rename "because it has full codebase awareness"
Sounds like a strength but inverts the rule — broad awareness doesn't prevent attention dilution across dozens of files; it's exactly why a large scoped task needs a subagent's narrower focus instead.
⚠ NEWTrap 5 — Batching all reported issues into one message
Feels efficient, but if some issues are independent and only one is a real dependency, batching risks conflating which feedback applies to which fix. Resolve the dependency first, then sequence the independents.
✓ Clarifying Insight
context: fork and plan mode solve different problems — they are not substitutes. Plan mode prevents costly mistakes by understanding the problem space before implementation. context: fork prevents verbose skill output from consuming the main session's context window. Both may be relevant in the same scenario at the same time.

Multi-Agent Research System

A coordinator agent decomposes complex research topics, delegates to specialized subagents (web search, document analysis, synthesis), and produces a unified, coherent research report.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D1 Agentic Architecture1.2, 1.3, 1.4Coordinator/subagent architecture; parallel Task calls; structured error propagation
D2 MCP Tool Design2.3, 2.5Least-privilege tool scoping per subagent role
D5 Context Management5.3, 5.5Partial results with coverage annotations; error recovery without full workflow failure
Key Concepts & Architectural Decisions
  • Coordinator routes all subagent outputs through a synthesis subagent — raw concatenation of outputs is an anti-pattern (Q7)
  • Parallel subagents = multiple Task calls in a single coordinator response — not across separate response turns
  • Subagents inherit nothing from coordinator — no history, no system prompt, no tool results — pass everything explicitly via Task invocation
  • Structured error context on failure: failure type + query attempted + partial results + alternative approaches — gives coordinator enough to recover intelligently (Q8)
  • Least privilege: give synthesis subagent only the simple verify_fact tool — not the full web search tool set (Q9)
  • Dependency-aware scheduling: only serialize at actual dependency boundaries; independent subagents launch in parallel immediately
  • Partial failure: return partial results with coverage annotations marking gaps — don't terminate the full workflow
  • NEWWhen a coordinator fans out to N subagents and only K succeed: fail the whole operation when the missing data is correctness-critical (e.g. a financial total with some accounts inaccessible — a 3-of-5 total presented as complete is worse than an error). Use-what-you-have is fine for supplementary/additive enrichment, but you MUST annotate which sources succeeded/failed and why. Also collect ALL failures across the fan-out — don't short-circuit on the first one.
  • NEWWhen two credible sources conflict on the same metric, preserve methodology context and publication/collection dates so "different measurement" reads as distinct from "different data." Include both values annotated and let the coordinator reconcile — don't auto-select by heuristic, halt immediately, or include both unflagged.
Exam Traps
⚠ Trap 1 — Parallel execution fixes synthesis quality (Q7)
Whether subagents run in parallel or sequentially has no effect on whether outputs are properly synthesized. The root cause of raw concatenation is a missing synthesis step — not execution order. Adding parallelism to a broken coordinator does not fix the synthesis anti-pattern.
⚠ Trap 2 — Over-provisioning synthesis subagent (Q9)
Giving the synthesis subagent the full web search tool set violates least privilege and clutters its decision space. A scoped verify_fact tool covers the common case; complex multi-source verification should route through the coordinator.
⚠ Trap 3 — Terminating workflow on single subagent failure (Q8)
One timeout is not grounds to kill the entire research workflow. Return structured error context, annotate coverage gaps, and proceed with partial results. The coordinator decides how to recover — the subagent's job is to propagate rich error context, not to terminate everything.
⚠ NEWTrap 4 — Returning partial data as if it were complete
Even when use-what-you-have is the right call, silently presenting a 3-of-5 result as a full one is a separate error from failing to fail — always annotate what succeeded and what didn't.
⚠ NEWTrap 5 — Auto-selecting a value when sources conflict
Picking "the more recent source" or averaging two conflicting numbers discards information the coordinator needs to reconcile properly. Preserve both, with dates and methodology.
✓ Clarifying Insight
The single most-tested concept in this scenario: subagents inherit nothing. When the exam presents a multi-agent failure — wrong outputs, repeated lookups, missing context — the root cause is almost always that something wasn't explicitly passed in the Task invocation. The fix is always "pass it explicitly," never "share it via session" or "inherit from coordinator."

Developer Productivity with Claude

Engineering teams configure Claude Code with shared conventions, file-type-specific rules, custom skills, and team commands to automate recurring developer workflows.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D3 Claude Code Workflows3.1, 3.2, 3.3, 3.5CLAUDE.md hierarchy; .claude/rules/ glob patterns; skills; team commands
D2 MCP Tool Design2.1, 2.2MCP server integration for developer tooling
D4 Prompt Engineering4.1, 4.2Structured developer-facing prompts; output format consistency across team
Key Concepts & Architectural Decisions
  • .claude/rules/ files with YAML frontmatter paths: ["**/*.test.tsx"] apply conventions automatically for matching file types — regardless of directory location (Q6)
  • CLAUDE.md hierarchy: ~/.claude/CLAUDE.md (user-local, never shared, not in git) → project CLAUDE.md (in git, visible to all teammates) → user CLAUDE.md (in git, user-specific overrides)
  • Skills: context: fork isolates verbose output; context: merge surfaces findings into the main session
  • PreToolUse/PostToolUse hooks enforce formatting or linting deterministically — prompt instructions cannot guarantee these
  • Team commands in .claude/commands/ provide shared slash commands without per-developer setup
  • NEWAll discovered CLAUDE.md files are CONCATENATED, not overriding. On conflict, more specific scope wins (directory > project > user). Same-scope conflicts may resolve arbitrarily — eliminate them rather than relying on load order. Keep each file under ~200 lines.
  • NEWA team MCP server needing a per-developer token belongs in project-level .mcp.json with ${VAR} expansion — each developer supplies their own token locally. A shared .env file listing every developer's token, even committed alongside .mcp.json, is still a secrets-in-git violation, just consolidated.
  • NEWTwo same-purpose tools/servers colliding by identity (system-prompt keyword matches a tool name; personal staging DB server vs. shared prod server) should be fixed at the thing that actually changed or belongs to you — rephrase the prompt, or make your own ~/.claude.json entry distinguishable — not by editing the shared .mcp.json or forcing tool_choice for the whole session.
  • NEWAn SSE-transport MCP server showing zero tools at Claude startup with no error means the server wasn't reachable at startup — SSE connects to an already-running server, and if it isn't up yet, it silently drops all its tools. Distinct from a missing mcp__ prefix in allowedTools, which blocks one specific tool that did load.
  • NEWRate limiting for a shared MCP server must be enforced server-side (token bucket in the server implementation) — the one point every request is forced through. A PreToolUse time.sleep() or a prompt instruction to "space out calls" is client-side and advisory; it doesn't stop a second agent session from overwhelming the server.
Exam Traps
⚠ Trap 1 — ~/.claude/CLAUDE.md for team conventions (Q6)
This file is user-local and is not part of the project repository. Teammates never see it. Shared team conventions belong in the project-level CLAUDE.md committed to git, or in .claude/rules/.
⚠ Trap 2 — Per-directory CLAUDE.md for cross-directory file types (Q6)
Creating a CLAUDE.md in each directory that contains test files cannot efficiently target *.test.tsx files spread across 20 subdirectories. .claude/rules/ with a glob pattern handles any file matching the pattern anywhere in the project with a single file.
⚠ Trap 3 — Relying on header inference in CLAUDE.md (Q6)
A ## Test file conventions section header in root CLAUDE.md does not automatically apply when test files are edited. Claude does not infer scope from section headers. Explicit paths: glob matching in .claude/rules/ is required for automatic activation.
⚠ NEWTrap 4 — A shared .env file "solves" the credential problem
Consolidating every developer's token into one committed file is not meaningfully different from hardcoding them individually — both put secrets in git. Use ${VAR} expansion instead.
⚠ NEWTrap 5 — Wrong-scoped fix on a tool/server identity collision
Renaming a tool that was already fine, forcing tool_choice for the whole session, or editing the shared .mcp.json to fix a personal-scope problem are all wrong-blast-radius fixes. Fix what actually changed or actually belongs to you.
✓ Clarifying Insight
CLAUDE.md hierarchy and .claude/rules/ solve different scoping dimensions. CLAUDE.md hierarchy controls which instructions are visible at which project level. .claude/rules/ controls which instructions activate for which file types. The exam consistently tests whether candidates can identify which dimension of scoping a given problem requires — they are not interchangeable.

Claude Code for CI/CD

Claude Code runs inside automated CI/CD pipelines for security analysis, test generation, PR review, and code quality reporting — without any interactive input.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D3 Claude Code Workflows3.6Non-interactive CI flags; machine-parseable output; CI-specific CLAUDE.md behavior
D4 Prompt Engineering4.5Batch API for overnight analyses vs. synchronous API for blocking pre-merge checks
D1 Agentic Architecture1.3Independent review instances; no same-session reasoning bias in CI flow
Key Concepts & Architectural Decisions
  • -p / --print flag: runs Claude Code in non-interactive (headless) mode — required for CI/CD pipelines (Q10)
  • --output-format stream-json: machine-parseable output for pipeline scripts [uncertain — verify exact flag syntax]
  • Pre-merge blocking checks (developers wait on result): synchronous API only — Batch API cannot guarantee the latency SLA (Q12)
  • Overnight/nightly jobs (tech debt, coverage): Batch API appropriate — 50% cost savings; no blocking latency requirement (Q12)
  • Generate + review in CI: two separate Claude instances — review instance receives only the artifact + review criteria; no generation context carries over
  • CI-specific CLAUDE.md: disable clarification prompts; enforce structured output format; no interactive confirmations
  • NEWA chained pipeline (generate → review → check-breaking-changes) must run each review/check step as an independent session, not sharing context with the generation step. Shared context biases the review toward agreeing with the generator's own reasoning instead of catching its errors — bias inheritance, not a formatting problem.
  • NEW--bare is not "quiet mode" — it skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md, and sets CLAUDE_CODE_SIMPLE. Docker still auto-discovers local config by default. -p/--print is the separate non-interactive flag; --batch and CLAUDE_HEADLESS don't exist.
  • NEWBatch job re-submission math: max interval = SLA_hours − 24h (batch window) − preprocessing_hours. Results return out of order — correlate by custom_id, never by array position. No per-request GET endpoint exists; poll until ended, then download one .jsonl results file.
Exam Traps
⚠ Trap 1 — Flags that don't exist (Q10)
--batch, CLAUDE_HEADLESS=true, and --no-config are all distractors referencing non-existent flags or environment variables. Only -p / --print is the documented non-interactive mode flag. If the option sounds plausible but you haven't seen it in docs, it's probably a distractor.
⚠ Trap 2 — Batch API for pre-merge checks (Q12)
Developers wait on pre-merge results in real time. The Batch API has a 24-hour processing window and no guaranteed latency SLA — completely unsuitable for any workflow where someone waits on the result. Cost savings do not override blocking latency constraints.
⚠ Trap 3 — Same-session generate + review
Using the same Claude session to generate code and then review it carries same-session reasoning bias. The review instance must be independent — supplied with only the code artifact and review criteria, not the generation context or reasoning chain.
⚠ NEWTrap 4 — "Fix it with better formatting" for an unreliable CI review step
If review/check output is noisy or self-contradictory, the instinct is to demand JSON or add formatting rules. If the root cause is shared-context bias inheritance from the generation step, no formatting fix touches it.
⚠ NEWTrap 5 — Treating --bare as just output suppression
It disables an entire layer of auto-discovered configuration (hooks, skills, plugins, MCP, memory, CLAUDE.md) — very different from quieting console noise.
✓ Clarifying Insight
Every Batch API question pairs a latency-sensitive workload with a latency-tolerant one. The discriminator is always: does someone wait on this result in real time? If yes → synchronous API. If no (overnight, nightly, weekly) → Batch API. The 50% cost savings are real — they just don't apply when blocking latency is a constraint.

Structured Data Extraction

Claude extracts structured fields from unstructured documents (invoices, contracts, medical records) at scale, with schema validation, semantic integrity checks, and human review workflows.

Primary Domains Tested
DomainSubdomainsWhy This Scenario Tests It
D4 Prompt Engineering4.3, 4.4, 4.5JSON schema design; tool_choice forced first call; Batch API for high-volume nightly runs
D5 Context Management5.5, 5.6Human review calibration; aggregate vs. segment-level accuracy analysis (Q11)
D2 MCP Tool Design2.2Structured error responses for extraction failures
Key Concepts & Architectural Decisions
  • JSON schema + strict: true eliminates syntax errors only — semantic errors (mismatched totals, invalid date ranges, mutually exclusive fields) require application-layer validation
  • Nullable fields ("nullable": true) prevent hallucination of absent data more reliably than required fields with "N/A" as a permitted string
  • Aggregate accuracy (97% overall) masks poor performance on specific document types or field segments — always verify segment-level before reducing human review (Q11)
  • tool_choice: {"type": "tool", "name": "extract_fields"} forces the first tool call — guarantees structured output format immediately, no natural-language preamble turn
  • Batch API: appropriate for high-volume overnight extraction runs (no real-time SLA) — not for user-facing synchronous extraction
  • Human review thresholds must be calibrated per document-type segment, not by overall confidence scores alone
  • NEWA flat enum field that keeps producing invalid combinations (a cardio metric on a strength-type record) needs a discriminated-union schema — anyOf/oneOf branches per type, each with its own required fields — or separate per-type tools. A flat enum can't bind two correlated fields.
  • NEWRetry-with-error-feedback is the wrong tool when required information is simply absent from the source — no retry invents data that isn't there. Retryable = info exists but extracted wrong (resend source + failed output + validator errors). Non-retryable = info absent (use nullable fields; don't force the model to fabricate a value).
  • NEWWhen extraction fails because a referenced document was never uploaded, further retries produce plausible hallucinations, not recovered data. Detect the absence after validation, stop retrying, mark the extraction incomplete, and request the document.
  • NEWReported per-field confidence ≠ measured accuracy — models are often overconfident (a stated 90% may be ~70% correct). Close the gap by measuring stated-vs-observed accuracy against labeled ground truth per document type, and feed corrections back — not one global threshold.
  • NEWWhen review capacity is limited (not just measuring accuracy), allocate it proportional to risk/consequence-of-error — heavy review on high-regulatory-exposure segments, light on low-risk ones. Distinct from segment-level accuracy measurement: that finds where accuracy is weak; this allocates limited effort once you know what's at stake. Don't use the model's self-reported confidence to decide what to skip.
Exam Traps
⚠ Trap 1 — 97% aggregate accuracy is reliable (Q11)
A document type extracting at 60% accuracy could be entirely hidden inside a 97% overall metric. The exam explicitly tests the insight that aggregate metrics mask segment failures. Always verify by document type and field segment before reducing human review — never assume aggregate accuracy is uniform.
⚠ Trap 2 — Schema catches all errors
JSON schema catches structural and syntax issues. It cannot verify: line-item totals match invoice totals, dates fall in valid business ranges, mutually exclusive fields don't coexist, or extracted values are semantically plausible. Application-layer programmatic validation is always required on top of schema conformance.
⚠ Trap 3 — Lower confidence threshold to reduce flagging (Q11)
Lowering the confidence threshold suppresses detection — it does not improve extraction accuracy. This approach would reduce human review rates precisely where the model is most likely to be wrong. Higher-risk segments need more review, not less.
⚠ NEWTrap 4 — A flat enum with more values fixes invalid field combinations
More enum values still can't express "field X is required only when type = Y." That needs a discriminated union or per-type tools.
⚠ NEWTrap 5 — Retrying any failed extraction on principle
Retry-with-error-feedback only helps when the source information exists but was extracted wrong. If the source document itself is missing, retrying manufactures a plausible but fabricated answer.
⚠ NEWTrap 6 — Using self-reported model confidence to decide what to skip reviewing
Confidence is a poorly-calibrated internal estimate, not a measured guarantee — a fluent-but-wrong high-risk extraction can still self-report high confidence. Allocate review capacity by actual risk, not the model's own confidence score.
✓ Clarifying Insight
Schema compliance and semantic accuracy are independent dimensions. A document can pass schema validation perfectly and still contain wrong values, totals that don't add up, or self-contradicting fields. The correct production architecture always layers: (1) schema conformance via tool_use + strict: true, (2) application-layer semantic validation, (3) segment-aware human review thresholds. Any answer implying schema alone is sufficient is wrong.
