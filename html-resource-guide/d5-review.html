1 Long Context and Attention Management (5.1)

Models reliably process content at the beginning and end of long inputs. Content in the middle may be missed — the "lost in the middle" effect. Key findings must go at the top.

The Lost-in-the-Middle Effect

Key finding positionModel reliability
Beginning of documentHigh — reliably processed
End of documentHigh — reliably processed
Middle of documentLow — may be ignored or under-weighted

Fix vs. Wrong Fixes

Correct Fix
  • Place key findings summaries at the BEGINNING of aggregated inputs
  • Use explicit section headers (=== KEY FINDING ===) to signal important content
  • Trim verbose tool outputs to relevant fields BEFORE they accumulate
Wrong Fixes
  • Pre-aggregate inputs to 20K tokens via summarization — loses specific values
  • Rotate which subagent's output appears first to "average out" position effects — doesn't fix position bias
  • Stream results incrementally — position bias still applies within each chunk

Tool Output Trimming

Verbose tool outputs accumulate with every API call. After 10 calls, a 40-field order object can consume 80%+ of your context window.

Symptom80% of context is tool results
Root causeTools return everything; coordinator passes everything forward
Fix at source (preferred)Upstream agent returns only relevant fields (5-field trimmed vs. 40-field verbose)
Reactive fixPostToolUse hook trims output after the fact
Wrong fixIncrease max_tokens — doesn't address what's filling context, just makes the window bigger

2 Escalation and Human-in-the-Loop (5.2)

The exam tests this heavily with scenario questions. The key: escalation triggers are about capability gaps and explicit requests — not customer emotion, not complexity.

Valid Escalation Triggers (escalate when ANY apply)

TriggerAction
Customer explicitly requests a human agentEscalate IMMEDIATELY — do not investigate first, do not offer to resolve first
Policy is silent or ambiguous on the specific requestEscalate — cannot proceed without guidance
Unable to make meaningful progress after reasonable attemptsEscalate with summary of what was tried

Do NOT Escalate Based On

These Are NOT Escalation Triggers
  • Customer frustration or emotional tone alone (sentiment ≠ complexity)
  • Self-reported confidence scores (poorly calibrated)
  • Multi-topic messages (handle each topic with appropriate tools)
  • "Case seems complex" without a specific policy gap or failure to progress

The Frustrated User Pattern (heavily tested)

Correct 3-Step Pattern

Step 1: Acknowledge frustration empathetically
Step 2: Offer to resolve the issue (if within capability)
Step 3: Only escalate if customer reiterates wanting a human AFTER your offer

Two Wrong Responses

Wrong A: Escalate immediately because they sound angry → frustration alone is not a trigger
Wrong B: Ignore the frustration and just process the request → acknowledge first

Fix for Miscalibrated Escalation

Correct fixAdd explicit escalation criteria with 3-4 few-shot examples to system prompt
Wrong: confidence thresholdSelf-reported confidence is unreliable — auto-escalation on low confidence doesn't work
Wrong: sentiment classifierFrustration ≠ complexity — sentiment doesn't predict whether escalation is needed

Multiple Account Matches

Lookup returns multiple accounts for "John Smith." Action: ask for an additional identifier (email, phone, order number).

Wrong: Select the most recent account via heuristic. Wrong: Select the highest-value account. Both risk acting on the wrong account.

3 Context Degradation and Memory Patterns (5.4, 5.5)

The Claude API is stateless — no session_id, no automatic history. Every request must include the full messages array. In long sessions, specific details pushed into the middle of a large context are forgotten — the model falls back to generic descriptions.

API Statelessness (5.5)

FactClaude API has NO session memory — every request is independent
RequirementEvery request must include the FULL messages array with all prior turns
50+ turn sessionsEvery request re-sends all history → linear cost growth
Exam trap"The Claude API retains state between calls" — FALSE. No session_id parameter exists.

Context Degradation (5.4)

Details
SymptomAgent says "typical patterns" or "standard approach" instead of the specific class/function it found earlier in the session
CauseSpecific findings pushed into the middle of long context; lost-in-the-middle effect
FixScratchpad files — agent writes discoveries to file, reads back at phase boundaries
Also helps/compact in Claude Code — summarizes conversation to reclaim token budget
Wrong fixAdd more instructions to an overloaded context (wrong tool for the problem)
Wrong fixLower max_tokens — max_tokens controls OUTPUT length, NOT session size

Scratchpad File Pattern

# Step 1: Agent discovers something → writes to scratchpad
with open("scratchpad.json", "w") as f:
    json.dump({"http_class": "LegacyHttpRequestWrapper",
               "db_pool": "LegacyDbPool.getInstance()"}, f)

# Step 2: At phase boundary → inject scratchpad at TOP of next question
content = (
    "=== KEY FINDINGS (from scratchpad) ===\n"
    f"{json.dumps(scratchpad, indent=2)}\n"
    "=== END SCRATCHPAD ===\n\n"
    "Question: Which class for HTTP requests?"
)

Hybrid Context Management for Long Sessions

For 50+ turn sessions, use all three together:

  1. Summarize older messages — condense early turns
  2. Keep recent turns verbatim — last few turns need exact detail
  3. Persistent case-facts block — outside summarized history; maintained by YOUR code

Case-Facts Block (5.5)

What It Is and Why It Works

A block of transactional facts (amounts, dates, order IDs, promo codes) maintained deterministically by your application code — not by Claude's summarization. It's included verbatim in every request, no matter how many times the conversation is summarized.

=== CASE FACTS (always reference these) ===
Customer ID: CUST-12345
Order ID: ORD-7890
Refund Amount Requested: $127.50
Promo Code: SUMMER25 (20% applied 2026-03-10)
Previous Resolution Attempts: replacement shipped twice, both incorrect
===
Wrong: raise summarization thresholdJust delays the problem — numbers still get lost eventually
Wrong: instruct Claude to preserve numbersProbabilistic — still degrades over time
Wrong: semantic DB retrievalMiss-detection risk on exact values (e.g., $127.50 vs. "about $130")

4 Structured Error Propagation (5.3)

When a subagent fails, it must return structured error context — not silence the failure or terminate the whole workflow. The coordinator uses this to make intelligent recovery decisions.

Structured Error Fields

FieldValuesPurpose
isErrortrue for failures; absent for success (even empty)Distinguishes access failure from successful empty result
errorCategory"transient" | "validation" | "business" | "permission"Determines recovery strategy
isRetryabletrue = retry may work; false = same params will fail againPrevents wasted retries on non-transient errors
descriptionWhat went wrong and what was attemptedEnables targeted recovery
partialResultsAny partial data from the failed operationDon't discard partial progress
suggestedAction"retry" | "fix_input" | "escalate" | "alternative_workflow"Guides coordinator decision

Critical Distinction: Error vs. Empty

Access/Execution Failure → isError: true
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "DB timed out"
}
Successful Query with No Results → NO isError
{
  "status": "success",
  "results": [],
  "count": 0,
  "message": "No records matched"
}
Conflating These Causes Cascading Bugs

If you return {"results": []} for a permission error → coordinator thinks query succeeded with no results → won't try alternative → user gets wrong answer with no indication of a problem.

Error Handling Decision Tree (6 Steps)

StepError typeAction
1Transient (timeout, network)Retry locally with backoff
2Validation (bad input format)Fix input, retry locally
3Permission / business ruleCan't retry — propagate structured error to coordinator
4Alternative source availableTry it — coordinator may route there
5Partial results onlyReturn partial + coverage annotations
6UnrecoverableEscalate to human with full context

Coverage Annotations

When a synthesis subagent compiles a report, it should annotate each topic with its coverage status. This lets the coordinator evaluate completeness and re-delegate only for specific gaps.

{
  "executive_summary": "Q1 revenue grew 15%...",
  "detailed_findings": {
    "revenue":      {"coverage": "well-supported", "sources": 3},
    "supply_chain": {"coverage": "gap",
                     "reason": "primary DB timed out; fallback not queried yet"},
    "international": {"coverage": "gap",
                      "reason": "requires restricted DB access"}
  },
  "coverage_summary": "2 of 4 topics well-covered. 2 gaps: supply_chain (retryable), international (permission required)."
}
Without annotationsCoordinator accepts incomplete output as done
With annotationsCoordinator re-delegates supply_chain to fallback; notes international gap in report

Anti-Patterns (Never Do These)

Anti-Patterns
  • Return {} or [] on failure (silent suppression) — coordinator can't recover
  • Terminate entire workflow on single subagent failure — disproportionate, loses partial progress
  • Retry with identical parameters on non-transient errors — will fail again
  • Discard partial results from timed-out subagents — return what you have + structured error

Question 1 of 12
A critical security alert appears in the middle of a long aggregated report. The model misses it in its summary. What is the correct fix?
A. Pre-summarize all inputs to 20K tokens so the model can process them as one chunk.
B. Place the key findings summary at the BEGINNING of the aggregated input with explicit section headers.
C. Rotate which source appears first to average out position effects.
D. Stream results incrementally to avoid the effect.
Models reliably process the beginning and end of long inputs. Place key findings at the top with clear section headers. Pre-summarizing loses specific values. Rotation and streaming don't fix position bias.
Question 2 of 12
A customer says: "I've been waiting 3 weeks for my refund, this is completely unacceptable!" What should the agent do?
A. Escalate immediately — strong emotion indicates a complex case.
B. Acknowledge the frustration, then look up the refund status and offer to resolve it.
C. Ignore the emotional tone and process the refund request silently.
D. Ask clarifying questions about why they're frustrated before taking action.
Frustration alone is NOT an escalation trigger. The correct pattern: acknowledge empathetically, then offer to resolve. Only escalate if the customer reiterates wanting a human AFTER you offer the resolution.
Question 3 of 12
The Claude API is called twice in sequence. The second call asks about something mentioned in the first. Without any changes, does the model remember the first call?
A. Yes — the API maintains a session cache for recent calls.
B. No — the API is stateless. The full messages array must be passed in every request.
C. Yes — if the calls happen within 5 minutes, they share a session.
D. Only if both calls use the same model version.
The Claude API is completely stateless. There is no session_id, no cache between calls. Every request must include the full messages array with all prior turns. Without it, the model has no memory of the previous call.
Question 4 of 12
A subagent searches a database and finds no records matching the criteria. How should it report this?
A. {"isError": true, "errorCategory": "transient", "description": "No data returned"}
B. {"status": "success", "results": [], "count": 0, "message": "No records matched criteria"}
C. {} — empty response indicates no results.
D. {"isError": false, "results": null}
An empty result is a SUCCESS — the query ran fine, nothing matched. isError should be absent (not false). Option A incorrectly treats empty result as an error, causing the coordinator to retry a successful query. Option C is silent suppression.
Question 5 of 12
After 15 turns of analyzing modules, an agent is asked "which HTTP class should I use?" and answers with generic advice instead of the specific class it found earlier. What is this called and how do you fix it?
A. Model hallucination — increase temperature.
B. Context overflow — lower max_tokens to prevent it.
C. Context degradation — use a scratchpad file to write and re-inject key findings at phase boundaries.
D. API statelessness — include more system prompt instructions.
Context degradation: specific findings pushed into the middle of a long context are lost. Scratchpad files persist findings outside the context window and are injected at the top of subsequent queries. max_tokens controls output length, not session size.
Question 6 of 12
A customer asks for a competitor price match. The support agent's policy covers own-site price adjustments only. What should the agent do?
A. Deny the request with a canned message.
B. Attempt to process it anyway using the closest policy.
C. Escalate to a human — this is a policy gap (competitor pricing not covered).
D. Ask the customer for proof of the competitor price before deciding.
Policy ambiguity or silence on the specific request is a valid escalation trigger. The policy covers own-site adjustments, not competitor matching — this is a gap. The agent can't resolve it with existing authority.
Question 7 of 12
A synthesis subagent returns: "Here is the complete research report on Q1 performance." The coordinator marks the task as done. What's the problem?
A. The report is too long — should be summarized first.
B. No coverage annotations — the coordinator can't tell if topics are well-covered or have gaps.
C. The coordinator should always verify reports independently before marking done.
D. The report should include a confidence score.
Without coverage annotations, the coordinator accepts incomplete output as done. With annotations, it can see which topics have gaps (source unavailable, permission denied) and re-delegate specifically for those gaps.
Question 8 of 12
In a long customer support conversation, summarization condenses "Customer referenced promo code SUMMER25 for 20% discount" to "Customer mentioned promotional pricing." How do you prevent this?
A. Raise the summarization threshold to delay when summarization kicks in.
B. Instruct Claude to always preserve exact numbers in summaries.
C. Maintain a case-facts block outside the summarized conversation, updated deterministically by your application code.
D. Store facts in a semantic database and retrieve them when needed.
Case-facts block: transactional data (amounts, codes, IDs) maintained by YOUR code, included verbatim in every request regardless of summarization. Raising the threshold just delays loss. Instructing Claude is probabilistic. Semantic retrieval risks miss-detection on exact values.
Question 9 of 12
A subagent gets a 403 Permission Denied when accessing a financial records table. What is the correct structured error response?
A. {"results": [], "count": 0} — empty result for empty access.
B. {"isError": true, "errorCategory": "permission", "isRetryable": false, "suggestedAction": "escalate"}
C. {"isError": true, "errorCategory": "transient", "isRetryable": true}
D. Terminate the workflow — if one step fails, the whole workflow is invalid.
Permission denied is non-transient (retrying with same params will fail again) → isRetryable: false. errorCategory: "permission". suggestedAction: "escalate". Option A is silent suppression — coordinator thinks query succeeded. Option C incorrectly marks it as transient/retryable.
Question 10 of 12
Context is filling up with verbose tool outputs (80% of context = order lookups). What is the correct fix?
A. Increase max_tokens to accommodate the larger context.
B. Switch to a model with a larger context window.
C. Have upstream agents return only relevant fields (trim at source), or use a PostToolUse hook to trim reactively.
D. Summarize tool outputs before passing them to the coordinator.
80% tool results = trimming problem, not a window size problem. Fix at source: agents return only the fields needed (5 fields not 40). PostToolUse hook is a reactive fix. Summarizing tool outputs loses specific values (same problem as pre-aggregation).
Question 11 of 12
An agent encounters a database timeout. According to the 6-step error handling decision tree, what is the first action?
A. Retry locally with backoff — transient errors should be handled locally first.
B. Propagate a structured error to the coordinator immediately.
C. Try an alternative data source.
D. Escalate to a human with the error details.
Step 1: Transient errors (timeout, network blip) → retry locally with backoff. Only if local retry fails do you propagate the error to the coordinator. Escalating immediately for a transient error is disproportionate.
Question 12 of 12
A customer says "I want to speak to a manager" mid-conversation while the agent is resolving a refund. What should the agent do?
A. Finish the refund first, then transfer to a manager.
B. Escalate immediately with a structured summary — explicit human request is honored without delay.
C. Explain that it can resolve the issue and offer to continue before transferring.
D. Ask why they want a manager to determine if escalation is truly necessary.
Explicit human request = escalate IMMEDIATELY. No investigation first, no offer to resolve first, no asking why. This is the highest-priority escalation trigger. Finishing the task first or questioning the request both violate the rule.
