Domain 5 — Context Management

CCA-F Exam Prep · 15% of exam · 7 subdomains

Long Context and Attention Management 5.1

Models reliably process content at the beginning and end of long inputs. Content in the middle may be missed — the "lost in the middle" effect. Key findings must go at the top.

The Lost-in-the-Middle Effect

Key finding positionModel reliability
Beginning of documentHigh — reliably processed
End of documentHigh — reliably processed
Middle of documentLow — may be ignored or under-weighted

Fix vs. Wrong Fixes

Correct Fix
  • Place key findings summaries at the BEGINNING of aggregated inputs
  • Use explicit section headers (=== KEY FINDING ===) to signal important content
  • Trim verbose tool outputs to relevant fields BEFORE they accumulate
Wrong Fixes
  • Pre-aggregate inputs to 20K tokens via summarization — loses specific values
  • Rotate which subagent's output appears first to "average out" position effects — doesn't fix position bias
  • Stream results incrementally — position bias still applies within each chunk

Tool Output Trimming

Verbose tool outputs accumulate with every API call. After 10 calls, a 40-field order object can consume 80%+ of your context window.

Symptom80% of context is tool results
Root causeTools return everything; coordinator passes everything forward
Fix at source (preferred)Upstream agent returns only relevant fields (5-field trimmed vs. 40-field verbose)
Reactive fixPostToolUse hook trims output after the fact
Wrong fixIncrease max_tokens — doesn't address what's filling context, just makes the window bigger

Never Summarize a Summary

Summarize Once, Carry Verbatim

Summarize the raw source ONCE into a durable structured artifact and carry it verbatim — each additional summarization pass loses numbers, dates, and edge-cases irreversibly. Restate critical constraints at the point of use; don't assume a fact 50k tokens back is recalled accurately.

Escalation and Human-in-the-Loop 5.2

The exam tests this heavily with scenario questions. The key: escalation triggers are about capability gaps and explicit requests — not customer emotion, not complexity.

Valid Escalation Triggers (escalate when ANY apply)

TriggerAction
Customer explicitly requests a human agentEscalate IMMEDIATELY — do not investigate first, do not offer to resolve first
Policy is silent or ambiguous on the specific requestEscalate — cannot proceed without guidance
Unable to make meaningful progress after reasonable attemptsEscalate with summary of what was tried

Do NOT Escalate Based On

These Are NOT Escalation Triggers
  • Customer frustration or emotional tone alone (sentiment ≠ complexity)
  • Self-reported confidence scores (poorly calibrated)
  • Multi-topic messages (handle each topic with appropriate tools)
  • "Case seems complex" without a specific policy gap or failure to progress

The Frustrated User Pattern (heavily tested)

Correct 3-Step Pattern

Step 1: Acknowledge frustration empathetically
Step 2: Offer to resolve the issue (if within capability)
Step 3: Only escalate if customer reiterates wanting a human AFTER your offer

Two Wrong Responses

Wrong A: Escalate immediately because they sound angry → frustration alone is not a trigger
Wrong B: Ignore the frustration and just process the request → acknowledge first

Fix for Miscalibrated Escalation

Correct fixAdd explicit escalation criteria with 3-4 few-shot examples to system prompt
Wrong: confidence thresholdSelf-reported confidence is unreliable — auto-escalation on low confidence doesn't work
Wrong: sentiment classifierFrustration ≠ complexity — sentiment doesn't predict whether escalation is needed

Multiple Account Matches

Lookup returns multiple accounts for "John Smith." Action: ask for an additional identifier (email, phone, order number).

Wrong: Select the most recent account via heuristic. Wrong: Select the highest-value account. Both risk acting on the wrong account.

Conflicting Preferences Over Turns

A user states a preference early ("I have low risk tolerance"), then later requests something contradictory ("recommend aggressive crypto strategies").

Correct: structured preference tracking — maintain a running preferences block updated each turn, surface the contradiction explicitly, and ask which takes precedence.

Both of These Are Wrong

Wrong A: Always escalate on any contradiction.
Wrong B: Always assume the latest preference wins and silently override the earlier one.

Avoiding Hard Truths Is NOT a Trigger

Don't Escalate to Dodge a Difficult Conversation

When verifiable evidence contradicts a customer's claim (e.g., tracking shows the package was delivered and signed for), present the evidence. Do NOT escalate just to avoid the difficult conversation — that is not a valid escalation trigger.

Clarify vs. Assume Framework

Weigh cost-of-wrong-assumption against friction-of-asking.

High cost + low frictionAlways clarify — cheap to ask, expensive to be wrong
Low cost + high frictionReasonable to assume with transparency

Structured Handoff Fields (by context type)

ContextRequired handoff fields
Customer supportCustomer ID · root cause · refund amount · recommended action
Research systemsResearch topic · disputed claims · source citations · analysis performed · recommended reviewer decisions
Anti-patternAttach the raw transcript and expect the reviewer to reconstruct context — use a structured summary instead

Structured Error Propagation 5.3

When a subagent fails, it must return structured error context — not silence the failure or terminate the whole workflow. The coordinator uses this to make intelligent recovery decisions.

Structured Error Fields

FieldValuesPurpose
isErrortrue for failures; absent for success (even empty)Distinguishes access failure from successful empty result
errorCategory"transient" | "validation" | "business" | "permission"Determines recovery strategy
isRetryabletrue = retry may work; false = same params will fail againPrevents wasted retries on non-transient errors
descriptionWhat went wrong and what was attemptedEnables targeted recovery
partialResultsAny partial data from the failed operationDon't discard partial progress
suggestedAction"retry" | "fix_input" | "escalate" | "alternative_workflow"Guides coordinator decision

Critical Distinction: Error vs. Empty

Access/Execution Failure → isError: true
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "DB timed out"
}
Successful Query with No Results → NO isError
{
  "status": "success",
  "results": [],
  "count": 0,
  "message": "No records matched"
}
Conflating These Causes Cascading Bugs

If you return {"results": []} for a permission error → coordinator thinks query succeeded with no results → won't try alternative → user gets wrong answer with no indication of a problem.

Error Handling Decision Tree (6 Steps)

StepError typeAction
1Transient (timeout, network)Retry locally with backoff
2Validation (bad input format)Fix input, retry locally
3Permission / business ruleCan't retry — propagate structured error to coordinator
4Alternative source availableTry it — coordinator may route there
5Partial results onlyReturn partial + coverage annotations
6UnrecoverableEscalate to human with full context

Coverage Annotations

When a synthesis subagent compiles a report, it should annotate each topic with its coverage status. This lets the coordinator evaluate completeness and re-delegate only for specific gaps.

{
  "executive_summary": "Q1 revenue grew 15%...",
  "detailed_findings": {
    "revenue":      {"coverage": "well-supported", "sources": 3},
    "supply_chain": {"coverage": "gap",
                     "reason": "primary DB timed out; fallback not queried yet"},
    "international": {"coverage": "gap",
                      "reason": "requires restricted DB access"}
  },
  "coverage_summary": "2 of 4 topics well-covered. 2 gaps: supply_chain (retryable), international (permission required)."
}
Without annotationsCoordinator accepts incomplete output as done
With annotationsCoordinator re-delegates supply_chain to fallback; notes international gap in report

Absent Source Document → HALT, Don't Retry

When a required input document was structurally NOT included in the model input (e.g., an approval letter is referenced but was never uploaded), automated retries produce plausible hallucinations, not recovered data — the model fills in what it "expects" to see.

Correct Response
  • Detect the absence programmatically after validation
  • Stop automated retries
  • Mark the extraction incomplete
  • Request the missing document from the user

Distinct from a format error (may be fixable) and a timeout (retryable).

Two Wrong Responses

Wrong A: Require the field and instruct Claude to infer it from nearby dates → produces hallucinated values.
Wrong B: Retry with increasingly explicit prompts → same hallucination at higher token cost.

Fail-Entire vs. Use-What-You-Have (Partial Results)

SituationDecisionWhy
Missing subagents hold correctness-critical data (e.g., a financial total across accounts)FAIL-ENTIREA 3-of-5 total presented as complete is worse than an error
Failing subagents are supplementary / additive enrichmentUSE-WHAT-YOU-HAVE + annotate what's missingNever present partial data as if complete
Any fan-out failureDo NOT short-circuit on the first errorCollect ALL failures before deciding

Anti-Patterns (Never Do These)

Anti-Patterns
  • Return {} or [] on failure (silent suppression) — coordinator can't recover
  • Retry when the source document is absent — produces hallucinations; detect absence and request the document instead
  • Present a partial aggregation (e.g., 3 of 5 accounts) as if it were complete
  • Short-circuit the fan-out on the first subagent error — collect ALL failures
  • Terminate entire workflow on single subagent failure — disproportionate, loses partial progress
  • Retry with identical parameters on non-transient errors — will fail again
  • Discard partial results from timed-out subagents — return what you have + structured error
Context Degradation and Memory Patterns 5.4

When specific findings are pushed into the middle of a long context window, the model falls back to generic responses instead of referencing them — this is context degradation, not hallucination. The fix is deterministic persistence outside the context window via scratchpad files.

Context Degradation

Details
SymptomAgent says "typical patterns" or "standard approach" instead of the specific class/function it found earlier in the session
CauseSpecific findings pushed into the middle of long context; lost-in-the-middle effect
FixScratchpad files — agent writes discoveries to file, reads back at phase boundaries
/compact behaviorSummarizes older turns, keeps recent turns verbatim — project CLAUDE.md is re-read from disk after compacting. Use when context is filling but session is still valid.
/clear vs /compact/clear = full wipe (use when prior tool results are stale). /compact = summarize and continue (use when context is large but still valid).
Wrong fixAdd more instructions to an overloaded context — makes it worse, not better
Wrong fixLower max_tokens — max_tokens controls OUTPUT length, NOT session size

Scratchpad File Pattern

# Step 1: Agent discovers something → writes to scratchpad
with open("scratchpad.json", "w") as f:
    json.dump({"http_class": "LegacyHttpRequestWrapper",
               "db_pool": "LegacyDbPool.getInstance()"}, f)

# Step 2: At phase boundary → inject scratchpad at TOP of next question
content = (
    "=== KEY FINDINGS (from scratchpad) ===\n"
    f"{json.dumps(scratchpad, indent=2)}\n"
    "=== END SCRATCHPAD ===\n\n"
    "Question: Which class for HTTP requests?"
)

Attention Dilution vs. Token Budget — Diagnosis Order

When an agent drifts or forgets after N turns and the context window was NOT full, the mechanism is attention dilution / recency bias — not token-budget exhaustion. Diagnose attention first, budget second. "Increase the context window" is almost never correct for a forgetting symptom.

Attention dilutionToken budget exhaustion
SymptomsReferences "typical patterns" instead of specific entities found earlier; stops following custom conventions; rule adherence degrades over turnsstop_reason: max_tokens; truncated responses; explicit "context full" signals
Right fixesConvert rules to few-shot examples · scratchpad re-read at phase boundaries · periodic summary injectionCompact / trim / restructure the accumulated context

Proactive Explore Subagent vs. Reactive /compact

Explore Subagent (proactive)

Runs a verbose discovery phase in its isolated context and returns a compact summary to the main session — preserving main-session headroom for implementation. Use it when the verbose output hasn't been generated yet.

/compact (reactive)

/compact runs AFTER context is already full. Using it instead of an Explore subagent when the verbose output hasn't been generated yet is the wrong tool for a proactive problem.

CLAUDE.md Is Not a Findings Store

CLAUDE.md captures policy/conventions, NOT live discovery findings. Relying on it for cross-session consistency in discovery work fails — spreading multi-phase work across sessions makes consistency harder.

Session and Window Management 5.5

The Claude API is stateless — no session_id, no automatic history. Every request must include the full messages array. In long sessions, transactional specifics (amounts, codes, IDs) are at risk of being lost through summarization — only deterministic, code-managed persistence keeps them safe.

API Statelessness

FactClaude API has NO session memory — every request is independent
RequirementEvery request must include the FULL messages array with all prior turns
50+ turn sessionsEvery request re-sends all history → linear cost growth
Exam trap"The Claude API retains state between calls" — FALSE. No session_id parameter exists.

Hybrid Context Management for Long Sessions

For 50+ turn sessions, use all three together:

  1. Summarize older messages — condense early turns
  2. Keep recent turns verbatim — last few turns need exact detail
  3. Persistent case-facts block — outside summarized history; maintained by YOUR code

Case-Facts Block

What It Is and Why It Works

A block of transactional facts (amounts, dates, order IDs, promo codes) maintained deterministically by your application code — not by Claude's summarization. It's included verbatim in every request, no matter how many times the conversation is summarized.

=== CASE FACTS (always reference these) ===
Customer ID: CUST-12345
Order ID: ORD-7890
Refund Amount Requested: $127.50
Promo Code: SUMMER25 (20% applied 2026-03-10)
Previous Resolution Attempts: replacement shipped twice, both incorrect
===
Wrong: raise summarization thresholdJust delays the problem — numbers still get lost eventually
Wrong: instruct Claude to preserve numbersProbabilistic — still degrades over time
Wrong: semantic DB retrievalMiss-detection risk on exact values (e.g., $127.50 vs. "about $130")

Auto Memory Location

Exam Trap — Auto Memory Path

Wrong: Auto memory is in .claude/memory/ (project-level, version-controlled).
Correct: Auto memory is in ~/.claude/projects/<project>/memory/ — user-level, NOT version-controlled. First 200 lines or 25KB loaded at session start.

Do separate git worktrees each get their own auto memory? No — all worktrees and subdirectories within the same git repository share ONE auto memory directory. It is not duplicated per worktree (and not shared across machines).

Conflicting Source Data and Synthesis Quality 5.6

When subagents return conflicting values from different sources, the correct response is to include both values with source attribution and let the coordinator decide how to reconcile — not to auto-select one via heuristic or halt the workflow.

Handling Conflicting Values

ActionCorrect?Why
Include both values, annotated with source attributionYes — alwaysPreserves information; lets coordinator reconcile
Auto-select one value via credibility heuristic (more recent, higher authority)NoHeuristics discard valid data; coordinator loses visibility
Halt analysis and escalate immediately when conflict is foundNoComplete the analysis first; flag the conflict, don't abort
Include both values without flagging the discrepancyNoCoordinator can't act on a conflict it doesn't know about

Source Attribution Loss During Summarization

When findings are compressed into prose summaries, the connection between claims and their sources disappears. A 2020 statistic and a 2024 statistic become indistinguishable — or look contradictory rather than temporal.

Correct Fix — Structured Claim-Source Mappings

Require subagents to output structured claim-source mappings (not prose summaries) that the synthesis agent is explicitly instructed to preserve. Include publication/data collection dates in every structured output.

Anti-Pattern — Prose Summary

Subagent returns: "Market share is approximately 34%." Source and date are gone. If another subagent returns 28%, the coordinator cannot tell whether these are from different years, different methodologies, or a genuine conflict.

Structured Claim-Source Mapping Example

{
  "claim": "Market share: 34%",
  "source": "Industry Report Q4 2024",
  "date_collected": "2024-12-01",
  "confidence": "high"
},
{
  "claim": "Market share: 28%",
  "source": "Competitor Analysis Q2 2020",
  "date_collected": "2020-06-15",
  "confidence": "medium",
  "note": "Temporal discrepancy — older data, not a contradiction"
}

Render Content by Type

Financial dataTables — preserves exact values and comparability
News / narrativeProse — natural format for sequential events
Technical findingsStructured lists — preserves specificity
Wrong: uniform proseConverting everything to prose loses precision on financial/technical content

Distinguishing Established vs. Contested Findings

Structure synthesis output to distinguish well-established findings from contested ones, preserving the original source characterizations. Do not flatten contested data into a single authoritative-sounding claim.

Methodology Differences vs. Data Conflicts

Two credible sources can report different statistics because they measure the same construct differently — not because one is wrong. Annotate conflicts with methodology context, not just source attribution. Without methodology, consumers can't tell "different data" from "different measurement."

Provenance, Recency, and Uncertainty Properties

Provenance is per-CLAIMNot per-response — a "sources: [A,B,C]" header doesn't say which source backs which claim; every claim carries its own sources
Recency is advisoryNot decisive — a 2019 peer-reviewed paper can outweigh yesterday's blog post
Uncertainty propagatesA claim drawn from conflicting sources inherits lower confidence, regardless of how clean the prose reads

Accuracy Measurement and Human Review Calibration 5.7

Aggregate accuracy metrics (e.g., 97% overall) can mask poor performance on specific document types or fields. Never reduce human review based on aggregate metrics alone — validate by document type AND by field before changing review thresholds.

Why Aggregate Accuracy Is Not Enough

MetricWhat It Tells YouWhat It Hides
97% aggregate accuracyOverall system performs well on averageMay mask 60% accuracy on handwritten forms or rare document types
Field-level accuracyWhich specific fields are underperformingNothing — this is the correct granularity
Document-type accuracyWhich document categories cause failuresNothing — required before reducing review

Stratified Random Sampling

Correct Sampling Approach

Sample from high-confidence extractions across all document types and fields — not just a random sample of the overall output. High-confidence extractions are where the system is most likely to have novel failure patterns that aggregate metrics won't surface.

PurposeMeasure actual error rates per segment; detect novel failure patterns
Stratify byDocument type (forms, contracts, invoices) AND field (amounts, dates, signatures)
Wrong: random sample onlyRare document types are underrepresented — failures go undetected

Field-Level Confidence Scores

Calibrate confidence scores using labeled validation sets — not self-reported model confidence. Route review attention to genuinely uncertain extractions based on calibrated field-level scores, not a uniform confidence threshold across all fields.

Calibrated field scoresTrained on labeled examples — reflects actual error probability per field type
Uniform threshold (wrong)Same cutoff for all fields ignores that some fields are inherently harder to extract
Self-reported confidence (wrong)Model confidence is poorly calibrated — use labeled validation sets instead

The Calibration Gap

A stated 90% confidence may be only ~70% correct in practice — confidence is the model's internal estimate, not a measured guarantee.

Closing the Gap
  • Measure stated-vs-observed accuracy against a labeled ground-truth set
  • Do it PER document type — a model calibrated on invoices may be overconfident on purchase orders
  • Feed reviewer corrections back so calibration improves over time
  • Set review thresholds per type, not one global threshold

Priority-Ordered Review Queue

Order the human-review queue by lowest confidence × highest impact first — NOT FIFO. Reviewer attention goes where it changes outcomes most.

Before Reducing Human Review — Checklist

Required Before Reducing Review
  • Validate accuracy by document type — not just in aggregate
  • Validate accuracy by field — not just in aggregate
  • Analyze which document types or fields are underperforming
  • Use stratified sampling across all segments — not uniform random
  • Calibrate field-level confidence scores against labeled validation sets

Question 1 of 18
A critical security alert appears in the middle of a long aggregated report. The model misses it in its summary. What is the correct fix?
A. Pre-summarize all inputs to 20K tokens so the model can process them as one chunk.
B. Place the key findings summary at the BEGINNING of the aggregated input with explicit section headers.
C. Rotate which source appears first to average out position effects.
D. Stream results incrementally to avoid the effect.
Models reliably process the beginning and end of long inputs. Place key findings at the top with clear section headers. Pre-summarizing loses specific values. Rotation and streaming don't fix position bias.
Question 2 of 18

B. Acknowledge the frustration, then look up the refund status and offer to resolve it.
C. Ignore the emotional tone and process the refund request silently.
D. Ask clarifying questions about why they're frustrated before taking action.
Frustration alone is NOT an escalation trigger. The correct pattern: acknowledge empathetically, then offer to resolve. Only escalate if the customer reiterates wanting a human AFTER you offer the resolution.
Question 3 of 18
The Claude API is called twice in sequence. The second call asks about something mentioned in the first. Without any changes, does the model remember the first call?
A. Yes — the API maintains a session cache for recent calls.
B. No — the API is stateless. The full messages array must be passed in every request.
C. Yes — if the calls happen within 5 minutes, they share a session.
D. Only if both calls use the same model version.
The Claude API is completely stateless. There is no session_id, no cache between calls. Every request must include the full messages array with all prior turns. Without it, the model has no memory of the previous call.
Question 4 of 18
A subagent searches a database and finds no records matching the criteria. How should it report this?
A. {"isError": true, "errorCategory": "transient", "description": "No data returned"}
B. {"status": "success", "results": [], "count": 0, "message": "No records matched criteria"}
C. {} — empty response indicates no results.
D. {"isError": false, "results": null}
An empty result is a SUCCESS — the query ran fine, nothing matched. isError should be absent (not false). Option A incorrectly treats empty result as an error, causing the coordinator to retry a successful query. Option C is silent suppression.

Context degradation: specific findings pushed into the middle of a long context are lost. Scratchpad files persist findings outside the context window and are injected at the top of subsequent queries. max_tokens controls output length, not session size.
