Meta-pattern across almost every anti-pattern below: probabilistic / prompt-based control substituting for deterministic enforcement — a hook, a schema, a structured field, or a config change is available and the anti-pattern reaches for a prompt instruction instead. Naming which lever is missing is usually the fastest way to spot the correct answer.
D1

Agentic Architecture & Orchestration

27% · task statements 1.1–1.7

Parsing natural language for loop termination
Why it failsFree-text output is an unstructured, probabilistic signal — the model might phrase completion ambiguously, mention "done" mid-task, or never say anything termination-shaped at all. There's no guarantee the wording maps reliably to actual state.
Do insteadBranch deterministically on the API's own stop_reason field: tool_use → continue the loop, end_turn → stop. This is a structured signal the harness controls, not prose the model happens to produce.
Arbitrary iteration caps as the primary stop mechanism
Why it failsA cap tells you the loop was cut off — not that the task actually finished. Treating "hit the limit" as the main success signal means you can't distinguish a completed task from one truncated mid-work.
Do insteadUse stop_reason as the primary signal; keep the iteration cap only as a safety-net circuit breaker underneath it, not the thing you check first.
Omitting the max_turns guard entirely Most common anti-pattern
Why it failsWithout any circuit breaker, a malfunctioning or looping agent can run indefinitely — burning tokens and cost with no forced exit, even though stop_reason is doing its job correctly in the happy path.
Do insteadAlways include a turn-count exit alongside stop_reason-driven control flow, even when the cap is never expected to trigger.
Using assistant text content as the completion signal
Why it failsSame root problem as parsing natural language for termination — text presence or absence isn't a structured, reliable indicator that the task is actually done.
Do insteadstop_reason, not text content, is the thing to branch on.
Raw concatenation of subagent outputs
Why it failsIndependent subagents can produce conflicting, overlapping, or incoherent results when simply stitched together — nobody reconciles them into one coherent answer.
Do insteadRoute all subagent outputs through a dedicated synthesis subagent that reconciles, dedupes, and prioritizes before producing the final result.
D2

Tool Design & MCP Integration

18% · task statements 2.1–2.5

Over-provisioning tools to an agent
Why it failsPast roughly 15 tools (the exam's own example: 18 vs. a recommended 4–5), decision complexity degrades selection reliability — the agent has more plausible options to weigh and misrouting becomes common.
Do insteadScope tightly: 2–4 tools for a specialized subagent, 4–6 for a general agent. Consolidate or split into purpose-specific tools rather than handing out the whole toolbox.
Collapsing every failure into one generic error string ("Operation failed")
Why it failsA uniform message gives the agent no way to distinguish retryable transient errors from permanent validation problems from permission failures — it ends up retrying things that will never succeed, escalating things it could fix itself, or hiding real access problems.
Do insteadReturn structured errors: errorCategory (transient/validation/business/permission), isRetryable, human- and customer-readable descriptions, and a suggestedAction.
Renaming one overlapping tool without rewriting its description
Why it failsDescription content — not the tool name — is what actually drives model tool-selection. A rename with the same description leaves the same functional ambiguity in place.
Do insteadRename and rewrite both overlapping tools so the functional overlap is genuinely removed, not just relabeled.
A shared .env file with every developer's token, committed to the repo
Why it failsConsolidating every developer's literal token into one file that still gets committed is the same secrets-in-git exposure as hardcoding them directly — the location changed, the exposure didn't. One leak now exposes every developer's credential instead of just one.
Do insteadProject-level .mcp.json (shared, version-controlled) with ${VAR} environment-variable expansion — each developer's token resolves from their own local environment at runtime and never enters a committed file at all.
D3

Claude Code Configuration & Workflows

20% · task statements 3.1–3.6

Team CI guidance placed in ~/.claude/CLAUDE.md
Why it failsUser-level CLAUDE.md is machine-local and never version-controlled — it isn't shared with the team, and on ephemeral CI runners it isn't present at all, so the guidance silently does nothing in the pipeline.
Do insteadPut team/CI-relevant instructions in project-level ./CLAUDE.md or ./.claude/CLAUDE.md so they're checked in and available wherever the repo is checked out.
Slash-command body text as a tool restriction ("only use Read and Write")
Why it failsSlash commands only support $ARGUMENTS substitution — prose in the command body describing restrictions is just text, and enforces nothing at the tool-call level.
Do insteadUse a Skill (.claude/skills/name/SKILL.md) — only SKILL.md frontmatter supports allowed-tools, which is actually enforced.
Chained CI steps (generate → review → check) sharing one session
Why it failsThe review/check steps inherit the generation step's own reasoning and justification as prior context — they anchor on it rather than independently re-deriving correctness, so they're biased toward agreeing with the very output they're supposed to catch errors in.
Do insteadRun each review/check step as an independent session with no shared context — it evaluates the output cold, from the diff alone.
Accepting a known-flawed plan, expecting execution-time hooks to catch it
Why it failsPlan mode is a pre-execution planning phase — it doesn't gate individual steps mid-run. A PreToolUse hook can block a specific tool call, but it can't retroactively fix a plan built on a flawed approach.
Do insteadRefine the plan itself in plan mode before approving it; use PreToolUse hooks for step-level gating, not as a substitute for a sound plan.
D4

Prompt Engineering & Structured Output

20% · task statements 4.1–4.6

Vague instructions ("be conservative," "only report high-confidence findings")
Why it failsThese are named failing instructions, not actionable criteria — the model has no concrete threshold to apply, so behavior doesn't reliably change.
Do insteadDefine explicit severity criteria per level with concrete code examples showing what qualifies at each tier.
Uniform strictness reduction across all categories to fix noisy output
Why it failsTurning down strictness everywhere penalizes categories that were already accurate, just to quiet down the few that were generating false positives.
Do insteadTemporarily and asymmetrically disable or de-emphasize only the high-false-positive categories (e.g. style, naming) while leaving accurate categories untouched.
Self-review in the same session/instance
Why it failsThe same instance retains its own generation reasoning as prior context and anchors on it — it's reviewing its own justification, not evaluating the output fresh, so it's biased toward agreeing with itself rather than catching design flaws it already reasoned into.
Do insteadUse an independent review instance with a fresh context window. Self-critique is still valid for completeness checks (did I cover timelines/next steps) — just not for catching flaws baked into the original reasoning.
Retrying with error feedback when the required info is simply absent from the source
Why it failsNo retry produces information that was never in the document to begin with — retrying just burns calls without changing what's available to extract.
Do insteadDistinguish retryable (info exists, extracted wrong) from non-retryable (info absent). Use nullable fields so the model reports null/unclear instead of fabricating a value to satisfy a required field.
A flat enum for fields that are actually correlated
Why it failsA flat exercise_type-style enum can't express which fields are valid together — it keeps allowing invalid combinations (e.g. a cardio metric attached to a strength exercise) because nothing in the schema ties field validity to the selected type.
Do insteadUse a discriminated-union schema (anyOf/oneOf branches per type, each with its own required fields), or separate per-type tools.
D5

Context Management & Reliability

15% · task statements 5.1–5.6

Sentiment or self-reported confidence as an escalation trigger
Why it failsSentiment detects frustration, not case complexity — an angry-but-solvable case doesn't need a human. Self-reported model confidence is poorly calibrated and doesn't reliably track actual correctness or difficulty.
Do insteadEscalate on narrow, explicit triggers: an explicit human request (honor immediately), a genuine policy gap or exception, or repeated attempts with no meaningful progress.
Silent suppression of errors (returning an empty result as success)
Why it failsConflating "zero results" with "the query failed/timed out" hides real access problems as valid, successful empty data — the agent has no way to tell a genuinely empty answer from a broken one.
Do insteadZero rows is a successful result; a timeout or access failure must set isError: true so it's never mistaken for valid empty data.
Terminating the entire workflow on one subagent's failure
Why it failsOne failed subagent doesn't mean every other subagent's results are invalid — killing the whole workflow discards otherwise-good partial work over a single, possibly-recoverable failure.
Do insteadLet unaffected subagents complete; surface the failure with structured error context (what failed, what was attempted, what's missing) and annotate coverage gaps rather than discarding everything.
Attaching a raw transcript instead of a structured summary for review
Why it failsForces the reviewer to reconstruct context from scratch, inflates tokens, and risks losing key facts (numbers, dates, commitments) in the middle of a long, unstructured transcript.
Do insteadMaintain a structured "case facts" block outside the progressively-summarized history, and hand the reviewer that structured summary, not the raw conversation.
