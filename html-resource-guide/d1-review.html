Agentic Loop Control Flow 1.1

stop_reason is the ONLY termination signal. Never parse response text to determine if the loop is done. Never check for phrases like "I have completed."

The Four stop_reason Values

stop_reasonMeaningAction
"end_turn"Agent is done — final responseExtract text, exit loop
"tool_use"Agent wants to call tool(s)Execute ALL tool_use blocks, return ALL results in ONE message
"max_tokens"Response was TRUNCATED — not completeRaise max_tokens and retry — do NOT treat as end_turn
"stop_sequence"Hit a defined stop sequenceExit loop (intentional stop)
max_tokens Trap

stop_reason: "max_tokens" means the response was truncated mid-generation. The agent is NOT done — it ran out of space. Double max_tokens and retry with a continuation prompt. Do NOT treat it as completion.

The Tool Call Loop Pattern

while True:
    response = client.messages.create(...)
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        return final_text    # Done

    if response.stop_reason == "max_tokens":
        max_tokens *= 2      # Truncated — not done
        continue

    if response.stop_reason == "tool_use":
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,   # links result to specific call
                    "content": json.dumps(result)
                })
        # ALL results in ONE message
        messages.append({"role": "user", "content": tool_results})

Parallel Tool Calls

When the model returns multiple tool_use blocks in a single response, it is requesting parallel execution. The pattern is identical — execute all blocks, return all results in one message.

Wrong — One Result Per Message
for block in tool_use_blocks:
    messages.append({"role": "user", "content": [one_result]})  # WRONG
    # This sends a partial result before the model has all the data
Correct — All Results in One Message
tool_results = [execute_tool(b) for b in tool_use_blocks]
messages.append({"role": "user", "content": tool_results})  # ONE message

Multi-Agent Coordinator / Subagent Architecture 1.2

Subagents do NOT inherit coordinator context. Every subagent starts fresh. Pass everything it needs explicitly via system prompt + task message. The coordinator's full conversation history is invisible to subagents.

Coordinator Pattern (4 Steps)

  1. Decompose the task into scoped subtasks with explicit context
  2. Dispatch in parallel — multiple Task calls in one response turn (not sequential)
  3. Collect structured outputs (JSON, not prose) from all subagents
  4. Synthesis pass — dedicated subagent integrates findings; never concatenate raw outputs

Dependency-Aware Parallel Scheduling

Only serialize at actual dependency boundaries — everything without a dependency runs from the start. Holding independent agents until unrelated dependencies clear is wasted parallelism.

ScenarioAction
A, B, E, F are all independentLaunch all four in parallel immediately
C depends on A onlyStart C as soon as A completes — don't wait for B
D depends on A + BStart D only when both A and B complete
Hold E and F until D finishesWrong — E and F have no dependency on D, start them immediately

Coordinator Instruction Style

Wrong — Step-by-Step Procedures

"First call get_customer, then call get_orders, then format the result as follows..." — over-specifies implementation, reduces agent flexibility.

Correct — Goals + Quality Criteria

"Return a JSON object with the customer's top 3 open orders, including status and amount. Accuracy over speed."

Subagent Context Passing 1.3

Context must be explicitly injected into every Task invocation. Subagents have zero access to the coordinator's conversation history, tool results, or system prompt — pass everything needed via the task message, using structured data not prose.

What Subagents Receive

What to passStructured JSON or CSV — preserves exact values across handoffs
What NOT to passConversational prose summaries — paraphrasing loses specificity
IncludeSource attribution (URLs, doc names, page numbers) in structured format
ScopeEach subagent gets only tools relevant to its role — no cross-specialization access

Why Structure Beats Prose

Wrong — Prose Reference
task = "Analyze what we discussed about the order processing pipeline"
# Subagent has no "what we discussed" — returns generic output
Correct — Explicit Context Injection
task = f"Analyze: {json.dumps(order_pipeline_context)}"
# Full context explicitly injected — subagent has everything it needs

Tool Sequencing and Programmatic Prerequisites 1.4

Prompt instructions have a non-zero failure rate for hard compliance. For operations that MUST run in sequence (verify identity → then process refund), enforce the prerequisite inside the tool itself — not only in the system prompt.

Two Enforcement Layers

Soft Layer (Probabilistic)

System prompt: "Always call verify_customer before process_refund." The model usually follows this — but can skip it on rare inputs or adversarial prompts.

Hard Layer (Deterministic)

process_refund checks shared state at the start: if not verified → return structured error. This fires regardless of what the model does.

def process_refund(customer_id, amount, reason):
    # PROGRAMMATIC GATE — fires regardless of model behavior
    if not state.customer_verified:
        return {
            "success": False,
            "blocked_by": "prerequisite_gate",
            "error": "PREREQUISITE NOT MET: Call verify_customer first."
        }

Model-Driven Tool Selection

Good tool descriptions eliminate the need for routing classifiers. The model selects tools based on intent and descriptions. A keyword classifier in front of the agent is a sign that tool descriptions need to be improved.

Wrong — Keyword Routing Classifier
if "refund" in user_message.lower():
    require_verification()
# Fails on paraphrasing: "Can I get my money back?" doesn't match "refund"
Correct — Clear Tool Descriptions + Gate in Tool

Description: "Process a refund for a verified customer. Requires prior successful verify_customer call — will fail with error if unverified."

Hooks: PreToolUse + PostToolUse 1.5

Hooks give you deterministic guarantees. System prompt instructions give you probabilistic compliance. For business rules that MUST always hold, use hooks. Prompts are suggestions. Hooks are laws.

Hook Types

HookWhen it firesWhat it can do
PreToolUseBefore a tool executesAllow (exit 0), block (exit 2), warn (exit 1), or modify input via updatedInput
PostToolUseAfter a tool executesInject additional context alongside the result before the model processes it

Hook Exit Codes — The Exam Tests This

Exit codeBehaviorNote
exit 0Allow — tool runs normallyStandard allow
exit 2Blocking — tool cannot execute; hook output shown to userThis is the "ask user" / hard-block code
exit 1 (or other non-zero)Non-blocking warning — tool runs anyway, warning displayedDoes NOT block execution
Exit Code Trap

Exit 1 does NOT block the tool — it just shows a warning and lets the tool run. Exit 2 is the blocking code. Most developers assume exit 1 = block. Wrong.

PreToolUse: Production Path Gate

# hook_pre_production_gate.py
import json, sys
hook_data = json.load(sys.stdin)
tool_input = hook_data.get("tool_input", {})   # UNWRAP — not top level
file_path = tool_input.get("file_path", "")

if "/production/" in file_path.replace("\\", "/"):
    print(json.dumps({
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "ask",
            "permissionDecisionReason": f"Write to production path: {file_path}. Approve?"
        }
    }))
    sys.exit(2)   # blocking — pause, ask user

sys.exit(0)       # allow

Hook stdin — The Wrapping Trap

# WRONG — file_path is not at the top level
hook_data = json.load(sys.stdin)
file_path = hook_data.get("file_path", "")   # always returns ""

# CORRECT — Claude Code wraps params one level deep under "tool_input"
hook_data = json.load(sys.stdin)
tool_input = hook_data.get("tool_input", {})
file_path = tool_input.get("file_path", "")

# Full stdin shape:
# {
#   "hook_event_name": "PreToolUse",
#   "tool_name": "Write",
#   "tool_input": { "file_path": "...", "content": "..." },
#   "session_id": "...",
#   "tool_use_id": "..."
# }

PostToolUse: PII Trimming Limitation

# hook_post_pii_trim.py — injects PII warning context alongside tool result
import json, sys
print(json.dumps({
    "hookSpecificOutput": {
        "hookEventName": "PostToolUse",
        "additionalContext": "PII WARNING: treat any emails in result as [REDACTED]"
    }
}))
sys.exit(0)
PostToolUse PII Limitation

PostToolUse cannot replace the raw tool result — it only adds additionalContext alongside it. PII already in conversation history from earlier turns is NOT affected. For full PII prevention, sanitize at the source (in the tool itself).

Redirect-to-Alternative Pattern

When a PreToolUse hook blocks a policy-violating call, the denial message should also direct the agent to the correct alternative.

Example: block process_refund above $500 AND return "Refund exceeds $500 limit — call escalate_to_human instead." This enforces policy AND correct workflow in one step rather than leaving the agent stuck.

Task Decomposition Strategies 1.6

Two decomposition strategies — choose based on whether the scope is known upfront or discovered as you go.

Prompt Chaining vs. Adaptive Decomposition

Prompt ChainingAdaptive Decomposition
When to useSteps are KNOWN before execution startsSteps are DISCOVERED based on findings
ExamplePer-file review → cross-file review → rankingSecurity triage → generate targeted subtasks → execute subtasks
CharacteristicFixed sequential pipeline; each output feeds the nextTriage output determines what subtasks exist
Use forStructured reviews, predictable multi-aspect pipelinesOpen-ended investigations, unknown scope
Exam phrase"Fixed sequential pipeline""Generate subtasks based on what is discovered"

Large Codebase Review: Per-file + Cross-file Passes

Correct — Two Passes
  • Local pass (per-file): SQL injection, null checks, unused imports, off-by-one — all per-file issues
  • Cross-file pass (separate): inconsistent API contracts, authorization gaps spanning services, data model mismatches
  • Run local passes in parallel, then one cross-file integration pass with all local findings as input
Wrong — Single Pass on All Files

Attention dilutes across 14+ files. Local and cross-file issues blur together. Inconsistent review depth. Missing bugs from the middle. Contradictory feedback across files.

Cross-file Issues Are Invisible in Local Passes

# api_gateway.py calls get_orders(order_id) — but get_orders expects user_id
# This bug only appears when you see BOTH files together
# Per-file review of api_gateway.py alone misses it
# Per-file review of order_service.py alone misses it
# Only the cross-file integration pass catches it

Prompt chaining for open-ended security investigationsAdaptive decomposition — steps can't be written before triage runs

Session Management and Parallelism 1.7

Long-running investigations need structured state management. Two patterns: fork_session for divergent exploration, --resume for continuing named sessions. For pipelines that may be interrupted: crash recovery manifests.

Session Patterns

PatternWhen to useWhat it does
fork_sessionYou want to try two different approaches from the same starting pointCreates independent branches from a shared analysis baseline — like git branches for agent sessions
--resume [session-name]Continuing a named investigation across work sessionsInjects prior context back into a new session — avoid when prior tool results are stale
Fresh start + injected summaryFiles have changed significantly since last sessionNew session + explicit summary of prior findings — more reliable than resuming stale context

Resume vs. Fresh Start Decision

Resume whenPrior tool results are still current — files haven't changed, context is still valid
Fresh start whenPrior tool results are stale or files changed significantly — inform the new session about what changed
When resumingTell the session specifically which files changed rather than requiring full re-exploration

Crash Recovery with Manifests

For long-running multi-agent pipelines that may be interrupted:

  1. Each subagent exports structured state to a fixed known path (JSON manifest)
  2. Coordinator loads the resume manifest on restart
  3. Injects manifest into new subagent prompts → recovery without restarting from scratch
Wrong Recovery Approaches
  • Freeform scratchpad (manually updated prose) — unreliable, lacks machine-readable structure
  • Resuming prior session + inferring from history — unreliable when prior tool results are stale
Correct: Machine-Readable Manifest

Programmatically loadable JSON at a fixed path. Coordinator reads it, determines what's done vs. remaining, injects only relevant state into new prompts.
