1 Tool Descriptions and Selection (2.1)

Tool descriptions are the primary mechanism Claude uses for tool selection. Overlapping or vague descriptions cause misrouting. When two tools overlap, fix BOTH descriptions — not just one.

Bad vs. Good Description Anatomy

Bad — Vague, Overlapping
find_orders: "Find orders for a customer. Use this to look up order information."
get_order:   "Get order details. Use this to retrieve information about an order."
# Both say the same thing — Claude can't distinguish them reliably
Good — Renamed, Differentiated, Explicit Boundaries
search_orders_by_criteria:
  "Search for a LIST of orders by name, email, date, or status.
   Returns summary list. Do NOT use when customer provides a specific order ID."

get_order_by_id:
  "Retrieve COMPLETE details for ONE order using a specific ID (ORD-XXXXX).
   Use ONLY when the customer provides a specific order ID.
   Do NOT use for browsing or searching across multiple orders."

Good Description Formula

When to useExplicit trigger conditions for this specific tool
Do NOT use whenExplicit exclusions that reference the other tool by name
NameMakes the boundary clear in the name itself (search_orders vs. get_order_by_id)
Fix both toolsOne unfixed tool still creates ambiguity — must fix both

tool_choice: "auto" + stronger prompts to force a specific tool"auto" can still return text; use tool_choice: "any" or forced selection
2 Tool Error Handling (2.2)

Structured error responses tell the agent HOW to recover. Generic or silent errors leave the agent unable to reason about next steps. "0 results" is NOT an error — it is a successful query returning an empty set.

Error Response Fields

FieldValuesMeaning
isErrortrueAccess or execution FAILED — absent for success (even empty results)
errorCategory"transient"Network/service issue — retry with same params may work
"validation"Bad input or policy violation — same params will fail again
"permission"Access denied — not retryable
isRetryabletrueAgent can retry with same parameters
falseAgent must change approach or escalate
descriptionstringCustomer-safe — NEVER echo raw input or PII back

The Critical Distinction

Access Failure → isError: true
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Service temporarily unavailable."
}
Empty Result → NO isError
{
  "status": "success",
  "results": [],
  "count": 0,
  "message": "No products matched."
}
Silent Suppression Anti-Pattern

Returning {} or [] for a failure → agent thinks the call succeeded → won't retry → won't try alternative → user gets wrong answer. Always return structured isError: true for actual failures.

Three Scenarios Compared

3 Tool Scope and Constraints (2.3)

Constraints should live inside the tool definition and implementation — not in the system prompt. System prompt constraints are probabilistic. Tool-level validation is deterministic.

Generic vs. Scoped Tool

Wrong — Generic Tool + System Prompt Constraint
fetch_url: "Fetch the content of any web URL."
# System prompt: "Only use our official documentation URLs"
# → Probabilistic — model may ignore the instruction
Correct — Scoped Tool with URL Validation in Implementation
load_support_doc: "Load from support.example.com or docs.example.com only.
                   Do NOT use for external sites — this tool rejects them."

def load_support_doc_impl(url):
    if not any(domain in url for domain in ALLOWED_DOMAINS):
        return {"isError": True, "errorCategory": "validation",
                "isRetryable": False,
                "description": "URL outside allowed domains. Use support.example.com only."}
    ...

Too-Many-Tools Problem

Having 15+ overlapping tools degrades tool selection reliability. The model misroutes between tools with similar names and descriptions.

Tool CountEffect
2-4 specialized toolsHigh reliability — model picks correctly
4-6 general-purpose toolsGood — acceptable complexity
6+ overlapping toolsDegraded reliability — misrouting increases
15+ toolsSignificant misrouting — consolidation required
FixConsolidate overlapping tools into focused ones with clear boundaries
Not the fixRename with numbered suffixes (order_lookup_v2) — just adds more similar names

Subagent Tool Restriction

Each subagent gets ONLY the tools relevant to its role:

  • Web-search subagent: search tools only
  • Document-analysis subagent: read tools only
  • Report-generation subagent: write tools only
  • No cross-specialization access — scoped per role

Give all subagents access to all toolsEach subagent gets only the tools for its role — scoped access
4 MCP Configuration (2.4)

MCP (Model Context Protocol) servers expose tools to Claude. Configuration lives in .mcp.json files. Credentials must use environment variable expansion — never hardcoded strings.

Sample MCP Config Structure

{
  "mcpServers": {
    "database": {
      "command": "python",
      "args": ["-m", "my_mcp_server"],
      "env": {
        "DB_HOST": "${DB_HOST}",
        "DB_PASSWORD": "${DB_PASSWORD}",   // env var expansion — NEVER hardcode
        "DB_NAME": "production"
      }
    },
    "files": {
      "command": "node",
      "args": ["file-server.js"],
      "env": {
        "API_KEY": "${FILE_SERVER_API_KEY}"
      }
    }
  }
}
Credential Pattern

Always use ${ENV_VAR} expansion for credentials. Never put actual API keys, passwords, or tokens as literal strings in the config file. The config can be committed to git; secrets should not be.

MCP Scopes

ScopeConfig fileWho it's for
Project.mcp.json in project rootTeam-wide MCP servers, version-controlled
User~/.claude/mcp.jsonPersonal MCP servers, machine-local

MCP Resources vs. Tools

MCP ToolsFunctions the model can call — like API calls (execute_query, send_message)
MCP ResourcesData sources the model can read — like files, database tables, documentation
Key distinctionTools = actions; Resources = data access. Both exposed via MCP server.

Rate Limiting — Where It Belongs

Wrong — Rate Limiting in Prompts or Hooks

System prompt: "Wait 1 second between calls." PreToolUse hook: time.sleep(1). Both are probabilistic and unreliable.

Correct — Token Bucket in the MCP Server

Rate limiting belongs in the MCP server implementation — a token bucket or similar mechanism enforced server-side. This is deterministic regardless of what Claude does.

MCP resources are the same as MCP toolsTools = callable functions; Resources = readable data sources
User-scoped MCP servers shared via git pull~/.claude/mcp.json is machine-local — not shared via version control

When to use resourcesWhen an agent calls the same tool N times in a loop to build up a dataset → expose that data as an MCP resource instead. One read replaces N iterative tool calls.
5 Tool Output Design (2.5)

Tool output shape determines context quality. Verbose outputs accumulate across tool calls and degrade agent reasoning. Return only what Claude needs to answer the question — not everything from the backend.

Verbose vs. Trimmed Output

Verbose (Anti-Pattern) — 20+ fields

Internal SKUs, warehouse bins, audit timestamps, query plan hashes, replica IDs, shard keys, cache metadata — none of this helps Claude answer "is this in stock?" It just consumes context tokens.

Trimmed (Correct) — Only business-relevant fields
{
  "product_id": "WIDGET-001",
  "name": "Blue Widget Pro",
  "price": 89.99,
  "in_stock": true,
  "category": "Widgets",
  "description": "A high-quality blue widget."
}

Where Trimming Happens

Fix at source (preferred)Upstream tool/agent returns only relevant fields from the start
PostToolUse hook (reactive)Strips fields after the tool returns, before model sees them
Hook returns summary + rawWRONG — still sends full raw content to model. Return ONLY the trimmed version.

Edit → Read + Write Fallback

The Edit tool requires a unique match in the target file. If the same string appears multiple times, Edit fails. Fallback:

  1. Read the full file
  2. Replace all occurrences in application code (str.replace())
  3. Write the full file back

Pagination for Large Result Sets

When a tool could return 100K+ tokens of results, paginate:

{
  "entries": [...first page...],
  "returned": 10,
  "total": 7432,
  "next_page_token": "abc123"   // null on last page
}

Agent fetches subsequent pages only if the task requires them — avoids flooding context in a single call.

Question 1 of 12
Two tools (find_orders and get_order) have similar descriptions and Claude keeps misrouting. What is the correct fix?
A. Rename and rewrite only find_orders — the better description will clarify the distinction.
B. Rename and rewrite BOTH tool descriptions with explicit "when to use" and "do NOT use when" sections.
C. Add few-shot routing examples to the system prompt to teach the correct selection.
D. Add a routing classifier layer that parses the user message and picks the right tool.
Fix BOTH descriptions. One unfixed tool still creates ambiguity. Few-shot examples add overhead without fixing root cause. Routing classifiers are over-engineered — Claude already routes by description.
Question 2 of 12
A product search returns 0 results. How should the tool respond?
A. {"isError": true, "errorCategory": "transient", "description": "No data returned"}
B. {"status": "success", "results": [], "count": 0, "message": "No products matched."}
C. {} — empty dict for empty results.
D. {"isError": false, "results": null}
0 results is a SUCCESS. The query ran correctly — nothing matched. isError should be absent. Option A incorrectly treats this as an error, causing the agent to retry a successful query.
Question 3 of 12
A tool returns {"isError": true, "errorCategory": "validation", "isRetryable": false}. What should the agent do?
A. Retry with the same parameters after a brief delay.
B. Change approach or escalate — same parameters will fail again.
C. Retry once, then escalate if it fails again.
D. Ignore the error and return an empty response to the user.
isRetryable: false means same parameters will always fail. This is a validation or permission error — the input is wrong or access is denied. The agent must change approach (fix input, try alternative, or escalate). Retrying is wasteful.
Question 4 of 12
A tool has a URL parameter but should only fetch from support.example.com. Where should this constraint be enforced?
A. System prompt: "Only use support.example.com URLs."
B. Inside the tool implementation — validate the URL and return a structured error if it's outside the allowed domain.
C. In the tool description — write "only use for support.example.com."
D. In a PreToolUse hook that checks the URL before the tool executes.
Constraints belong in the tool implementation — deterministic enforcement. System prompt is probabilistic (model can ignore it). Description helps but doesn't enforce. PreToolUse hook also works, but fixing at the tool level is the primary recommendation for scope constraints.
Question 5 of 12
An MCP config file needs a database password. How should it be stored?
A. As a literal string: "DB_PASSWORD": "my_secret_password"
B. As an environment variable: "DB_PASSWORD": "${DB_PASSWORD}"
C. Encrypted in the config file using AES-256.
D. In a separate secrets.json file that's imported by .mcp.json.
Always use ${ENV_VAR} expansion. The config can be committed to git; secrets must not be. The environment variable is resolved at runtime from the system environment.
Question 6 of 12
A PostToolUse hook returns both a formatted summary and the raw tool output. What's the problem?
A. The hook runs too slowly, delaying the agent's response.
B. The full raw output is still sent to the model — context isn't saved. The hook should return ONLY the trimmed version.
C. Formatted summaries can't be parsed by the model.
D. No problem — giving Claude both options improves its reasoning.
If the hook returns both, the model sees both — verbose output still consumes context. Return ONLY the formatted/trimmed version. The purpose of the hook is to reduce what the model processes, not add to it.

Question 8 of 12
The Edit tool fails with "match is not unique." What is the fallback procedure?
A. Use Grep to find the unique occurrence, then Edit with more context.
B. Read the full file → modify all occurrences in application code → Write the full file back.

Edit requires a unique match. When it fails: Read full file → replace all occurrences in code (e.g., str.replace()) → Write full file back. This handles non-unique matches reliably.
Question 9 of 12
A tool description says "Retrieve information about an order." Why is this problematic?
A. It's too short — descriptions need to be at least 100 words.
B. It's vague — it doesn't specify when to use this tool vs. other order-related tools, causing misrouting.

Question 10 of 12
A tool returns an error description that includes the user's submitted promo code: "Invalid promo code: SUMMER25." What's wrong?
A. Nothing — echoing input helps the model understand the error context.
B. Error descriptions must be customer-safe — never echo raw input or PII back.

Error descriptions must never echo raw input — this includes promo codes, order IDs, customer data, or any user-provided value. Customer-safe: "The promotional code is not valid or has expired. Please try a different code."
