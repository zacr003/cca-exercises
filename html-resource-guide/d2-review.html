Domain 2 — MCP Tool Design

CCA-F Exam Prep · 18% of exam · 5 subdomains

Tool Descriptions and Selection 2.1

Tool descriptions are the primary mechanism Claude uses for tool selection. Overlapping or vague descriptions cause misrouting. When two tools overlap, fix BOTH descriptions — not just one.

Bad vs. Good Description Anatomy

Bad — Vague, Overlapping
find_orders: "Find orders for a customer. Use this to look up order information."
get_order:   "Get order details. Use this to retrieve information about an order."
# Both say the same thing — Claude can't distinguish them reliably
Good — Renamed, Differentiated, Explicit Boundaries
search_orders_by_criteria:
  "Search for a LIST of orders by name, email, date, or status.
   Returns summary list. Do NOT use when customer provides a specific order ID."

get_order_by_id:
  "Retrieve COMPLETE details for ONE order using a specific ID (ORD-XXXXX).
   Use ONLY when the customer provides a specific order ID.
   Do NOT use for browsing or searching across multiple orders."

Good Description Formula

When to useExplicit trigger conditions for this specific tool
Do NOT use whenExplicit exclusions that reference the other tool by name
NameMakes the boundary clear in the name itself (search_orders vs. get_order_by_id)
Fix both toolsOne unfixed tool still creates ambiguity — must fix both

Every Description Answers Three Questions

A complete tool description answers all three: what it does · when to use it · what it does NOT do. The third is the disambiguator people omit — an explicit "Do NOT use this for X" is what actually prevents misrouting.

Corollary — split signal: a mode / action parameter that switches the tool between fundamentally different behaviors (search vs. create vs. delete) is a signal to SPLIT the tool into purpose-specific tools — not a feature to keep. One tool, one job.

When It's NOT the Description — System-Prompt Keyword Sensitivity

A distinct diagnosis the exam tests: the tool descriptions are genuinely well-written and non-overlapping, yet whenever a user message contains a specific keyword, routing systematically skews to the wrong tool. The root cause is not the descriptions — it's keyword-sensitive instructions in the system prompt. The fix lives in the system prompt, not the tool layer.

The tell in the stem: it explicitly rules out description problems ("descriptions are fine / non-overlapping") and points at a specific token in user input. If you reach for "rewrite the descriptions" or "add few-shot examples" here, you're fighting the premise.

Diagnostic Decision Table — "Why is it misrouting?"

tool_choice — Force, Then Release

Three modes: auto (model decides whether to call a tool — may skip and return text instead), any (must call SOME tool, but picks which), {type:"tool", name:"..."} (must call that exact named tool).

Force a named tool only for a deterministic FIRST step that must produce structured output before the loop can proceed (e.g. always validate_input or plan_subtasks first). Once it resolves, switch back to auto so the agent reasons freely for the rest of the turn — leaving it forced blocks the agent from adapting afterward.

Don't reach for auto when a tool call is a hard contract of the turn (e.g. a mandatory logging step) — use any there instead.

Tool Error Handling 2.2

Structured error responses tell the agent HOW to recover. Generic or silent errors leave the agent unable to reason about next steps. "0 results" is NOT an error — it is a successful query returning an empty set.

Error Response Fields

FieldValuesMeaning
isErrortrueAccess or execution FAILED — absent for success (even empty results)
errorCategory"transient"Network/service issue — retry with same params may work
"validation"Bad or malformed input — fix the input; same params will fail again
"business"Action blocked by a business rule/policy — explain the policy, do NOT retry
"permission"Access denied / insufficient privilege — escalate; not retryable
isRetryabletrueAgent can retry with same parameters

descriptionstringHuman-readable detail for the agent's reasoning — may include internal specifics
customerFriendlyMessagestringSeparate, customer-safe rendering — NEVER echo raw input or PII back; this is what's safe to surface to the end user
suggestedAction"retry" / "fix_input" / "escalate" / "alternative_workflow"Machine-readable next step the agent's recovery logic can branch on directly

The Four Categories → Recovery Action

The exam-tested taxonomy is exactly four: transient / validation / business / permission. Each maps to a different correct recovery — memorize the mapping, because the tempting wrong answer usually swaps the recovery verb (e.g. "escalate" a business rule instead of "explain and stop").

errorCategoryisRetryableCorrect recovery
transienttrueRetry the call (optionally after retryAfterMs)
validationfalseAsk the user to correct the input, then resubmit
businessfalseExplain the policy; do NOT retry. The rule blocks the action.
permissionfalseEscalate to a human or higher-privilege flow
business vs. permission — the classic swap

business = the action is disallowed by rule ("refunds over $10k need approval") → explain the policy and stop. permission = the caller lacks rights that a higher-privilege actor has → escalate. A "requires manager approval" stem sounds like escalation but is a business rule — the tool's job is to report the block, not route the approval. If a distractor offers escalate for a policy block, it's bait.

The Critical Distinction

Access Failure → isError: true
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Service temporarily unavailable."
}
Empty Result → NO isError
{
  "status": "success",
  "results": [],
  "count": 0,
  "message": "No products matched."
}
Silent Suppression Anti-Pattern

Returning {} or [] for a failure → agent thinks the call succeeded → won't retry → won't try alternative → user gets wrong answer. Always return structured isError: true for actual failures.

Tool Scope and Constraints 2.3

Constraints should live inside the tool definition and implementation — not in the system prompt. System prompt constraints are probabilistic. Tool-level validation is deterministic.

Generic vs. Scoped Tool

Wrong — Generic Tool + System Prompt Constraint
fetch_url: "Fetch the content of any web URL."
# System prompt: "Only use our official documentation URLs"
# → Probabilistic — model may ignore the instruction
Correct — Scoped Tool with URL Validation in Implementation
load_support_doc: "Load from support.example.com or docs.example.com only.
                   Do NOT use for external sites — this tool rejects them."

def load_support_doc_impl(url):
    if not any(domain in url for domain in ALLOWED_DOMAINS):
        return {"isError": True, "errorCategory": "validation",
                "isRetryable": False,
                "description": "URL outside allowed domains. Use support.example.com only."}
    ...

Too-Many-Tools Problem

Having 15+ overlapping tools degrades tool selection reliability. The model misroutes between tools with similar names and descriptions.

Tool CountEffect
Specialized subagent — 2–4 toolsHigh reliability — tightly scoped to its role
General-purpose agent — 4–6 toolsGood — acceptable complexity
CoordinatorTask tool + whatever it needs for its own analysis — not bound by the subagent counts above
15+ toolsDecision complexity degrades selection reliability — misrouting becomes common; consolidate or split
FixConsolidate overlapping tools into focused ones with clear boundaries
Not the fixRename with numbered suffixes (order_lookup_v2) — just adds more similar names

Subagent Tool Restriction

Each subagent gets ONLY the tools relevant to its role:

  • Web-search subagent: search tools only
  • Document-analysis subagent: read tools only
  • Report-generation subagent: write tools only
  • No cross-specialization access — scoped per role

Scoped Cross-Role Tool — The Exception

Sometimes a subagent frequently needs a simple lookup owned by another role (e.g. a synthesis subagent that repeatedly needs verify_fact). Rather than routing every lookup back through the coordinator, grant that subagent a scoped, narrow-purpose tool directly — this cuts latency for high-frequency simple operations without handing it broad access.

Decision rule — grant a cross-role tool ONLY when all three hold:

  • (a) the subagent frequently needs the lookup,
  • (b) the operation is read-only, and
  • (c) it does NOT change state.

Keep state-changing tools (process_refund, escalate_to_human) coordinator-only.

MCP Configuration 2.4

MCP (Model Context Protocol) servers expose tools to Claude. Configuration lives in .mcp.json files. Credentials must use environment variable expansion — never hardcoded strings.

Sample MCP Config Structure

{
  "mcpServers": {
    "database": {
      "command": "python",
      "args": ["-m", "my_mcp_server"],
      "env": {
        "DB_HOST": "${DB_HOST}",
        "DB_PASSWORD": "${DB_PASSWORD}",   // env var expansion — NEVER hardcode
        "DB_NAME": "production"
      }
    },
    "files": {
      "command": "node",
      "args": ["file-server.js"],
      "env": {
        "API_KEY": "${FILE_SERVER_API_KEY}"
      }
    }
  }
}
Credential Pattern

Always use ${ENV_VAR} expansion for credentials. Never put actual API keys, passwords, or tokens as literal strings in the config file. The config can be committed to git; secrets should not be. (Note: the ${VAR} form is the exam-correct syntax — env://VAR is a common distractor.)

Transports — stdio vs. SSE

TransportHow it connectsLifetime / gotcha
stdioClaude launches the server as a local child process and talks over stdin/stdoutLifetime = the session — started and torn down with Claude
SSEClaude connects to an already-running HTTP server (Server-Sent Events)Must be reachable at startup — if it isn't, the whole server silently drops its tools (no error; the tools just never appear)

MCP Scopes

ScopeConfig fileWho it's for
Project.mcp.json in project rootTeam-wide MCP servers, version-controlled
User~/.claude.jsonPersonal MCP servers, machine-local
MCP config never lives in CLAUDE.md

MCP servers are configured only in .mcp.json (project) or ~/.claude.json (user). Adding an [mcp_servers] section to CLAUDE.md has no effect — it's a wrong answer. For Bedrock access, set CLAUDE_CODE_USE_BEDROCK=1 plus AWS credentials — not ANTHROPIC_API_KEY.

MCP Resources vs. Tools

MCP ToolsFunctions the model can call — like API calls (execute_query, send_message)
MCP ResourcesData sources the model can read — like files, database tables, documentation
Key distinctionTools = actions; Resources = data access. Both exposed via MCP server.

Static Resource vs. Resource Template

MCP resources come in two forms, both read-only context injection — never side-effecting actions (that's what tools are for):

Static resourceA fixed URI with a known MIME type — one concrete document (e.g. docs://runbook).
Resource templateAn RFC 6570 URI template (e.g. customers://{id}/profile) — ONE declaration covers an unbounded set without enumerating each URI. Claude resolves {id}→42 and fetches customers://42/profile.

The template is the read-side complement to exposing a catalog as a resource instead of making N iterative tool calls: parameterized access covers the whole family from a single declaration.

Rate Limiting — Where It Belongs

Wrong — Rate Limiting in Prompts or Hooks

System prompt: "Wait 1 second between calls." PreToolUse hook: time.sleep(1). Both are probabilistic and unreliable.

Correct — Token Bucket in the MCP Server

Rate limiting belongs in the MCP server implementation — a token bucket or similar mechanism enforced server-side. This is deterministic regardless of what Claude does.

Community vs. Custom MCP Servers

Use community MCP servers for standard integrations (Jira, GitHub, Slack) — they already exist and are maintained. Reserve custom MCP server development for proprietary or team-specific systems with no community equivalent.

Community serverStandard integrations — Jira, GitHub, Slack, Linear
Custom serverProprietary internal systems, bespoke APIs, team-specific tooling
WrongForce a proprietary system into a community server template

allowedTools — The mcp__ Prefix

Exam Trap

"github__*" in allowedTools is WRONG. The correct pattern is "mcp__github__*" — the mcp__ prefix is required for all MCP tool permissions.

Two MCP Surfaces — API Connector vs. Claude Code Config

The exam tests whether you conflate two different MCP configuration surfaces:

API-level MCP ConnectorMessages API mcp_servers array. The server's auth token goes inline in the array object — {type:"url", url, name, authorization_token}. This token authenticates the Anthropic API (acting as MCP client) TO the remote server — it lives in the request BODY, not a separate header. (The x-api-key header authenticates you to Anthropic — different auth, different purpose.)
Claude Code MCP config.mcp.json / claude mcp add, credentials via ${VAR} env-var expansion (see above).

Reaching for the .env/${VAR} mental model on an API-connector question is the designed trap — that pattern belongs to the Claude Code surface, not the Messages API.

Tool Avoidance = Description Problem

If an agent ignores a custom MCP tool and falls back to built-in primitives (Bash, grep), the root cause is a thin tool description — not a config or scope problem. If it were a config issue, the tool wouldn't load at all. The tool loads but loses the selection competition.

SymptomAgent uses Bash/grep instead of your custom MCP tool
Root causeTool description is too thin — no capabilities, no output shape, no guidance on when to prefer it
FixEnrich the description with what it does, what it returns, and explicit guidance ("prefer this over manual alternatives when X")
Wrong fixCheck the config or scope settings

Tool Output Design 2.5

Tool output shape determines context quality. Verbose outputs accumulate across tool calls and degrade agent reasoning. Return only what Claude needs to answer the question — not everything from the backend.

Built-In Tool Selection — The Funnel

The built-in tools form a narrowing funnel: Glob (find files by name) → Grep (find a symbol in file contents) → Read (offset/limit, not the whole file) → Edit (smallest change). Use absolute paths, and Read must precede Edit.

TaskCorrect toolWrong tool
Find files by name / path pattern (**/*.ts)GlobGrep, Bash find, Read on a directory
Search file contents (imports, callers, class names)GrepGlob (matches names, not contents)
Read an existing fileRead (with offset/limit)Bash cat; reading the whole file blindly
Targeted change at a unique anchorEditWrite (overwrites the whole file)
Create a new file or full rewriteWriteEdit (only for targeted changes)
Edit fails — anchor not uniqueExpand context / replace_all first; Read → modify → Write is the LAST resortJumping straight to Read+Write, or retrying Edit with the identical string
Long-running command + parallel workBash with run_in_background: trueBlocking Bash (halts all other work)

Large-repo understanding (500+ files): Glob for candidates → Read the few that matter → Grep for patterns across the rest. Never Read every file upfront — it blows the context window. When tracing an export renamed through wrapper modules (Logger→sysLog→appLogger), Grep each name in the chain separately; searching only the original name misses downstream callsites.

Verbose vs. Trimmed Output

Verbose (Anti-Pattern) — 20+ fields

Internal SKUs, warehouse bins, audit timestamps, query plan hashes, replica IDs, shard keys, cache metadata — none of this helps Claude answer "is this in stock?" It just consumes context tokens.

Trimmed (Correct) — Only business-relevant fields
{
  "product_id": "WIDGET-001",
  "name": "Blue Widget Pro",
  "price": 89.99,
  "in_stock": true,
  "category": "Widgets",
  "description": "A high-quality blue widget."
}

Where Trimming Happens

Fix at source (preferred)Upstream tool/agent returns only relevant fields from the start
PostToolUse hook (reactive)Strips fields after the tool returns, before model sees them
Hook returns summary + rawWRONG — still sends full raw content to model. Return ONLY the trimmed version.

Edit Recovery Order — Non-Unique Match

The Edit tool requires a unique match in the target file. If the same string appears multiple times, Edit fails. The correct recovery order (real-exam-confirmed):

  1. FIRST — expand old_string with more surrounding context so the match becomes unique, or use replace_all if every occurrence should change identically. Both stay inside the Edit tool.
  2. LAST resort — Read the full file, modify it, then Write it back. Only when no unique context exists at all, or for large-scale rewrites.

Defaulting straight to Read+Write without trying to expand context or replace_all first is the exam trap.

Pagination for Large Result Sets

When a tool could return 100K+ tokens of results, paginate:

{
  "entries": [...first page...],
  "returned": 10,
  "total": 7432,
  "next_page_token": "abc123"   // null on last page
}

Agent fetches subsequent pages only if the task requires them — avoids flooding context in a single call.

Two Routing Gotchas

PostToolUse fires on tool calls only

A PostToolUse hook triggers only when a tool is invoked — never on plain model text completions. You cannot use it to "check every response against a brand guide"; there's no tool call to hook.

Temperature is not a tool-selection lever

Raising temperature makes tool selection less reliable, not more "exploratory." It's an explicit wrong answer in routing questions — fix routing with descriptions and tool_choice, not temperature.

Question 3 of 21

An MCP server must expose read access to every customer's profile, and the customer set grows constantly. What's the right design?
A. Declare a separate static resource with a fixed URI for each customer profile.
B. Define a resource template — customers://{id}/profile — one declaration covering the unbounded set; Claude resolves {id} at read time.
C. Expose a get_customer_profile tool and call it once per customer in a loop.

A resource template uses an RFC 6570 URI template so one declaration parameterizes access to an unbounded set — Claude resolves {id}→42 and fetches customers://42/profile. A. Glob with **/*.ts.
B. Grep for the import string across file contents.
C. Read each file and scan for the import.
D. Bash find for the module name.
