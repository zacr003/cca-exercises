Domain 1 — Agentic Architecture (27%)

Concept 1 of 3 — The Agentic Loop
The Agentic Loop
  • Your code sends a request. Claude responds. You check the stop_reason field.
  • If stop_reason == "tool_use": execute the tool, add the result back, send again
  • If stop_reason == "end_turn": Claude is done. Print the response.
  • Anti-patterns to memorize:
  • Don't parse text for "I'm done" — text content is NOT a control signal
  • Don't set arbitrary iteration limits as the primary stop mechanism
  • Don't check if Claude said "complete"
  • Just read stop_reason. That's the only reliable signal.
TL;DR: The loop is: send request → check stop_reason → execute tool or stop. Nothing else.
Exam Tip: The exam tests whether you know the three anti-patterns. Memorize them. max_tokens = truncated (not complete) → raise max_tokens and retry.
Concept 2 of 3 — Hub-and-Spoke Architecture
Hub-and-Spoke (Coordinator/Subagent)
  • One coordinator breaks tasks down, delegates to specialized subagents, combines results
  • Each subagent has isolated context — they cannot see each other's work
  • The coordinator must explicitly pass all information between subagents
  • Common mistake: coordinator decomposes too narrowly, missing entire categories
  • Fix: give broad research goals, not narrow checklists
  • Emit multiple Task calls in a single coordinator response for parallelism — not across separate turns
TL;DR: Subagents are isolated. If the coordinator doesn't pass it, the subagent doesn't know it.
Exam Tip: The exam has questions about narrow decomposition causing incomplete coverage. Coordinator prompts should specify goals + quality criteria, not step-by-step procedures.
Concept 3 of 3 — The Enforcement Question: Prompts vs. Hooks
Prompts vs. Hooks — The Most Important Concept in the Cert
  • Prompts are probabilistic — they work most of the time, but not always
  • Canonical example: a well-crafted system prompt can still fail ~12% of the time
  • Hooks are deterministic — they physically block actions unless conditions are met. 100% enforcement.
  • Prompts = best for style, tone, formatting (occasional inconsistency acceptable)
  • Hooks = best for financial, compliance, security (one failure has real consequences)
TL;DR — Prompts are suggestions. Hooks are laws. When money is on the line, use hooks, not prompts.
Exam Tip: Q1 correct answer: A — programmatic prerequisite that blocks downstream tools. "PreToolUse hook" is always the correct answer when the scenario describes compliance/financial enforcement.
Trap: "A well-crafted system prompt" or "detailed instructions" are always the wrong answer for hard compliance scenarios.
Quick Reference
stop_reasonMeaningAction
"tool_use"Claude wants to call a toolExecute ALL tool_use blocks, return ALL results in ONE message
"end_turn"Claude is doneStop the loop, return result
"max_tokens"Response was TRUNCATEDRaise max_tokens and retry — do NOT treat as completion
"refusal"Claude declinedDo not retry identically

Domain 2 — Tool Design & MCP (18%)

Concept 1 of 3 — Tool Descriptions Matter
Tool Descriptions — The Highest-Leverage Fix
  • Tool descriptions are how Claude decides which tool to call
  • Vague, overlapping descriptions cause frequent misrouting
  • Fix: include input format, return type, and when to use this tool vs alternatives
  • Adding a "do NOT use this for…" line dramatically reduces errors
  • Better descriptions beat few-shot examples, routing layers, or any other fix
  • Fix both overlapping tools, not just one
TL;DR: The description IS the interface. Fix descriptions before trying anything more complex. Every wrong tool call costs tokens.
Exam Tip: Q2 correct answer: B — expand tool descriptions. If an agent ignores a custom tool and uses built-ins instead → the description is too thin, not a config problem.
Trap: "Add a routing classifier" or "add few-shot examples" are over-engineered wrong answers. Description first.
Concept 2 of 3 — MCP Server Scoping
Project vs. User Level MCP Configuration
  • MCP is how Claude connects to external tools like GitHub, Slack, databases
  • Project-level (.mcp.json): shared with team via git. Uses ${ENV_VAR} for secrets.
  • User-level (~/.claude.json): personal sandbox. Not shared. For experiments.
  • Use community MCP servers for standard integrations (GitHub, Slack, etc.)
  • Only build custom MCP for unique workflows not covered by community servers
  • Skills are more token-efficient than custom MCP for simple workflows
TL;DR: Project MCP = team tools (shared). User MCP = your playground (personal). Never hardcode secrets — use ${ENV_VAR}.
Exam Tip: Hardcoded secrets in .mcp.json = wrong. Always ${GITHUB_TOKEN} style. Team tools go in project-level config so they're version-controlled and shared.
Concept 3 of 3 — The Tool Overload Problem
Fewer Tools = Better Decisions
  • 18 tools = confused agent. 4–5 focused tools = precise, reliable agent.
  • tool_choice modes: "auto" (Claude decides), "any" (must use a tool, Claude picks), "forced" (must use this specific tool)
  • Pattern: force the right tool on step one, then switch to "auto" for the rest
  • Constraint makes agents precise — fewer choices = better decisions
  • 15+ tools → misrouting becomes common → split into specialized agents
TL;DR: Keep agents to 4–5 tools max. An agent with 18 tools makes worse decisions than one with 5. Constraint is a feature, not a limitation.
Trap: "tool_choice: any" forces tool use but lets Claude pick which one. "tool_choice: auto" may return plain text (no tool call). These are not the same.

Domain 3 — Claude Code Configuration (20%)

Concept 1 of 3 — The Configuration Hierarchy
Three Layers — Stop Dumping Everything in One File
  • User-level (~/.claude/CLAUDE.md): personal preferences — not shared via git
  • Project-level (.claude/CLAUDE.md): team rules and conventions — shared via version control
  • Path-specific (.claude/rules/*.md): conditional rules that only load for matching files
  • Example: testing rules only load when editing test files; API rules only in the API folder
  • This saves tokens and keeps Claude focused on what's relevant
  • Priority order: user > project > directory (all concatenated, not overridden)
TL;DR: CLAUDE.md is an instruction set, not a knowledge base. Split your monolith into three layers. Path-specific rules are the golden nugget — only load what applies.
Exam Tip: The paths: frontmatter key is what makes rules path-scoped (NOT projects: or directories:). Files under .claude/rules/ with paths: frontmatter only inject when editing matching files.
Trap: Directory-level CLAUDE.md loads on active generation/editing in that directory — NOT just from referencing files there.
Concept 2 of 3 — Commands vs. Skills vs. Plan Mode
When to Use What
  • Commands: reusable prompts triggered with /slash. Team-wide in .claude/commands/, personal in ~/.claude/commands/
  • Skills: runs in isolated context (context: fork). Defines allowed tools. Can prompt for arguments with argument-hint.
  • Plan mode: for complex, ambiguous, multi-file tasks. Claude explores without modifying anything.
  • Direct execution: for simple, single-file fixes. Don't over-plan straightforward changes.
  • All three share the same goal: keep the main conversation clean
TL;DR: Match the tool to task complexity. Skills isolate. Plan mode explores. Direct execution just does it.
Exam Tip: Skill frontmatter has exactly 3 valid keys: context, allowed-tools, argument-hint. Nothing else. context: fork is what enables isolation.
Trap: Commands are prompts (text injected into conversation). Skills are isolated sub-agents. They are not the same thing.
Concept 3 of 3 — Claude Code in CI/CD
Two Flags Turn Claude Code into an Automation Tool
  • -p flag: non-interactive. No prompts, no confirmations. Runs and returns the result.
  • --output-format json: structured output that other tools can parse
  • Together, these let you trigger Claude Code from any CI/CD pipeline
  • Critical: use a SEPARATE session for review. Same session that wrote the code is biased.
  • Fresh eyes — even AI eyes — catch more than self-review
  • --bare: skips all auto-discovery (CLAUDE.md, settings). Use for clean isolated runs.
TL;DR: Write in one session, review in a different one. Self-review is inherently biased by prior reasoning. A fresh instance is a genuinely independent reviewer.
Exam Tip: The CI/CD pattern always uses two separate Claude Code invocations: one to generate, one to review. Single-session review is explicitly the wrong answer.

Domain 4 — Prompt Engineering & Structured Output (20%)

Concept 1 of 3 — The Few-Shot Advantage
Why 2–3 Examples Beat a Full Page of Instructions
  • When Claude gives inconsistent output, show it 2–3 examples instead of writing more instructions
  • Claude doesn't memorize — it generalizes the pattern. Show null for missing data once, it uses null everywhere.
  • Few-shot examples also reduce hallucination in extraction tasks
  • 2–3 targeted, contrastive examples beat a paragraph of detailed instructions every single time
  • Contrastive = show what TO do AND what NOT to do side by side
  • Fix both overlapping tools when misrouting — not just one
TL;DR: Show, don't tell. Examples teach Claude judgment, not just format. That's why two examples outperform a page of instructions.
Exam Tip: "Add more detailed instructions" is always the wrong answer when the question describes inconsistent output. The correct answer is always "add few-shot examples."
Trap: 15 unambiguous typical-case examples don't fix an ambiguous-scenario failure. Target the failure mode with 2–4 contrastive examples for the edge cases specifically.
Concept 2 of 3 — Guaranteed JSON with tool_use
Structured Output That Never Breaks
  • Define a tool with a JSON schema. Force Claude to call it with tool_choice.
  • Make fields nullable when source data might be missing — prevents Claude from fabricating values
  • This eliminates syntax errors (malformed JSON) but NOT semantic errors (wrong values)
  • You still need validation loops for content correctness
  • Required fields with missing data → Claude fabricates. Nullable fields → Claude returns null.
TL;DR: tool_use + JSON schema = guaranteed valid JSON. But validate the values separately — schema only catches structure, not meaning.
Exam Tip: The exam distinguishes syntax errors (schema fixes these) from semantic errors (application code must fix these). Knowing this distinction is critical for D4 questions.
Trap: strict: true in schema → guaranteed syntax conformance only. "Revenue field always populated correctly" is NOT guaranteed by schema.
Concept 3 of 3 — The Validation Loop
Extract → Validate → Retry with Specific Feedback
  • Pattern: extract → validate → retry with SPECIFIC error feedback. Not "try again."
  • Good feedback: "revenue says 0 but document clearly states 4.2 million on page 3"
  • Know when to stop: if the data isn't in the source, retrying won't produce it
  • Claude will start fabricating if you push retries past the point of available information
  • Non-retryable = when information is genuinely absent from the source document
TL;DR: Retry with specific errors. Stop when the data isn't in the source. Validation is as much about knowing when to stop as catching errors.
Exam Tip: The exam asks what to do when retries aren't helping. Correct answer: the data is absent — mark as unextractable, not retryable. Do NOT keep retrying.
Trap: "Retry with feedback" is correct only when the data exists but was extracted incorrectly. If the data isn't there, retrying causes hallucination.

Domain 5 — Context Management & Reliability (15%)

Concept 1 of 3 — The Context Window Problem
Claude Reads Start and End Well. The Middle Gets Fuzzy.
  • "Lost in the middle" effect: Claude processes beginning and end reliably; may miss middle
  • Every tool result adds data to the middle — 40 fields when you need 5
  • Fix 1: pin key facts at the TOP of context in a summary block
  • Fix 2: trim verbose tool outputs to only relevant fields
  • Fix 3: delegate verbose exploration to subagents — their output stays in their context
  • A new session with a summary beats a stale, bloated conversation
  • /compact summarizes history; CLAUDE.md is re-read after. /clear is a full wipe with no preservation.
TL;DR: Pin key facts at top. Trim tool outputs. Delegate heavy research to subagents. Attention degrades on a long context window the same way it degrades on a long drive.
Exam Tip: The exam tests all three fixes. Correct answer combos: key-facts-at-top + trim tool output + delegate to subagent. "Increase context window" is never the correct fix.
Concept 2 of 3 — When to Escalate
Agent-to-Human Handoff Rules
  • Customer asks for a human: escalate immediately. No exceptions. No investigation first.
  • Policy is ambiguous: escalate with full handoff package (customer ID, root cause, what was tried)
  • Straightforward issue: resolve, but offer to transfer
  • Do NOT use sentiment analysis or confidence scores — both are unreliable proxies
  • Frustrated user + solvable issue: acknowledge → offer to resolve → only escalate if they reiterate wanting human
  • Escalation triggers: explicit human request, policy gap, inability to make meaningful progress
TL;DR: If they ask for a human, give them a human. No exceptions. Sentiment and confidence scores misfire on sarcasm, cultural differences, and edge cases — only explicit signals are reliable.
Exam Tip: Sentiment alone is NOT sufficient for escalation. "Customer seems frustrated" → try to resolve first. "Customer explicitly asks for human" → escalate immediately, no matter what.
Trap: Investigating before escalating when the customer explicitly asked for a human = wrong answer. Explicit request = immediate handoff.
Concept 3 of 3 — Error Propagation
Generic Errors Blind the Coordinator. Structured Errors Enable Recovery.
  • "Search unavailable" tells the coordinator nothing — it can't make intelligent recovery decisions
  • Structured errors include: what failed, what was attempted, partial results, alternatives
  • Now the coordinator can: retry, use cached data, switch sources, or note the gap
  • Silent suppression and total termination are both anti-patterns
  • Error fields: isError, errorCategory (transient/validation/permission), isRetryable, partialResults, suggestedAction
TL;DR: Never return a generic error. Include what broke, what was tried, and what could be done instead. Graceful failure = the system can recover.
Exam Tip: Exam scenarios give you "generic error" vs "structured error with context, partialResults, isRetryable." The structured answer is always correct.
Trap: "Terminate the workflow" on any subagent error = wrong. "Silently suppress and continue" = also wrong. Return structured context and let the coordinator decide.
