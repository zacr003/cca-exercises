1 Few-Shot Prompting (4.1, 4.2)

When detailed instructions alone produce inconsistent results, the fix is concrete contrastive examples — not stronger instructions. Examples teach the model what the boundary IS, not just what "typical" looks like.

Three Approaches (in order of effectiveness)

ApproachProblemResult
Vague instruction — "be conservative""Conservative" is undefined — model has no concrete boundaryInconsistent output
Explicit criteria only — "CRITICAL when: SQL injection, hardcoded creds..."Covers clear cases but misses ambiguous edge casesBetter but not reliable
Explicit criteria + contrastive examples—Consistent and accurate

What Makes Examples Contrastive

Contrastive (Correct)

Two similar-looking cases with different classifications + an explanation of WHY they differ. This teaches the boundary between categories.

Example 1: name = request.form['name']; print(f"Hello, {name}")  → OK
  "User input used only for display — no DB query, safe in context"

Example 2: user_id = request.args.get('id'); db.execute(f"... {user_id}")  → CRITICAL
  "User input in SQL string — difference from Example 1: goes into a DB query"
Wrong — Grouped / Unambiguous Examples

Showing 10-15 obvious examples of each category doesn't help. The model already handles obvious cases — it's the edge cases that need examples.

Grouping all CRITICALs together, then all HIGHs, doesn't teach discrimination between similar-looking cases from different categories.

High False Positive Rate in One Category

Correct fixTemporarily DISABLE that category while improving its criteria and examples
Wrong: uniform strictness reductionPenalizes accurate categories to fix one broken one
Wrong: switch to more capable modelDoesn't fix the prompt quality issue — just moves the problem to a more expensive model

Exam Trap Table — 4.1/4.2

TrapCorrect Pattern
"Be more conservative" fixes false positivesVague — model has no concrete definition of "conservative"
10-15 unambiguous examples improve accuracyTargets easy cases; doesn't help the edge cases causing errors
Grouped examples (all CRITICALs, then all HIGHs)Doesn't teach discrimination — use adjacent contrastive pairs
More capable model fixes classification inconsistencyPrompt quality is the problem; fix the prompt, not the model
2-4 examples are too few2-4 targeted contrastive examples outperform 15 unambiguous ones
2 Structured Output and JSON Schemas (4.3)

tool_use + JSON schema guarantees syntax compliance — no JSON errors, required fields present, enums enforced. It does not guarantee semantic correctness. Cross-field validation must happen in your application code.

What Schema Guarantees vs. What It Doesn't

Schema Guarantees (Syntax)
  • No JSON syntax errors
  • Required fields are present
  • Enum values are from the allowed list
  • Type constraints respected (string, number, etc.)
Schema Does NOT Guarantee (Semantics)
  • Line items actually sum to the total
  • Dates are in valid ranges
  • Model didn't fabricate a schema-valid value
  • Cross-field consistency

Key Schema Design Patterns

PatternWhyExample
Nullable fields for optional dataRequired field + absent data = model fabricates. Nullable = honest null."type": ["string", "null"] for invoice_number
enum + "other" + detail fieldCovers known values cleanly; handles unknowns without fabricationcurrency: ["USD","EUR","GBP","other"] + currency_detail when "other"
"unclear" enum valueHonest escape hatch instead of forcing a wrong guessdocument_type: ["invoice","receipt","credit_note","unclear"]
stated_total AND calculated_totalCross-validation catches discrepancies the model must flagBoth required; if they differ → conflict_detected = true
conflict_detected booleanMachine-readable flag for routing to human reviewTrue if totals disagree or data is inconsistent

Semantic Validation Layer (Application Code)

# Schema won't catch this — you must check it yourself
if abs(stated_total - calculated_total) > 0.02:
    errors.append("Total mismatch: stated vs. calculated")

if stated_total < 0:
    errors.append("Negative total — likely extraction error")

if currency == "other" and not currency_detail:
    errors.append("currency is 'other' but detail is null")

stop_reason Warning

Critical Exam Trap

stop_reason: "max_tokens" does NOT guarantee schema compliance. Only stop_reason: "tool_use" (or "end_turn" with tool forced) means the schema was completed. If the response was truncated by max_tokens, the JSON may be incomplete.

Exam Trap Table — 4.3

TrapCorrect Pattern
strict: true eliminates all errorsOnly eliminates syntax errors — semantic errors still possible
Required fields with "N/A" string for absent dataUse nullable: "type": ["string", "null"]
stop_reason: "max_tokens" guarantees schema complianceIt does NOT — truncated response may be incomplete JSON
Schema validates that totals add up correctlyThat's semantic validation — must be done in application code
3 tool_choice Configuration (4.4)

Three settings, three behaviors. Getting these confused is one of the most common exam traps in Domain 4.

The Three Settings

SettingBehaviorWhen to use
"auto"Model MAY call a tool OR return text — model decidesGeneral-purpose agents; tool use is optional
"any"Model MUST call SOME tool; it picks which oneMultiple valid schemas, unknown doc type — model picks the right tool
{"type":"tool","name":"X"}Model MUST call tool X specifically — no text, no other toolsGuarantee a specific schema on the first turn
"none"Prevents all tool use — text response onlyWhen you want to suppress tool calls entirely
Most Common Exam Trap

"tool_choice: 'any' forces a specific tool" — WRONG. "any" guarantees SOME tool is called; the model still chooses which one. To guarantee a specific tool, use {"type": "tool", "name": "X"}.

The Recommended Pattern: Force First, Auto After

Turn 1 → Forced | Turn 2+ → Auto
Turn 1: tool_choice = {"type": "tool", "name": "extract_metadata"}
  → Guaranteed metadata extraction, model CANNOT skip or return text

Turn 2+: tool_choice = "auto"
  → Model adapts: can call any tool, ask clarifying questions, or return final answer
  → Forced for all turns is too rigid — model can't adapt after first turn

Behavior with Conversational Questions

Message"auto""any"forced
"What is 2 + 2?"Returns text: "Four"Forced to call SOME tool — model picks one awkwardlyForced to call the named tool — ignores that it makes no sense
Document for extractionMight call tool OR return descriptionGuarantees a tool call; picks the right schemaGuarantees the specific named tool

Exam Trap Table — 4.4

TrapCorrect Pattern
"any" forces a specific tool"any" forces A tool — model still picks WHICH one. Use forced selection for a specific tool.
"auto" + stronger prompts guarantees a tool call"auto" still allows text even with strong prompts — use "any" or forced
"any" for all turns in a multi-turn workflowWorks but too rigid — model can't adapt or return final text. Use auto after turn 1.
Forced selection for all turnsSame problem — model always forced to call same tool even when done
4 Message Batches API (4.5)

The Batch API is for latency-tolerant, non-blocking work. It saves 50% on cost but provides no guaranteed latency SLA — up to 24 hours. Never use it for workflows where something is waiting on the result.

Use Batch vs. Don't Use Batch

USE Batch API
  • Overnight technical debt reports
  • Weekly security audits
  • Nightly test generation
  • Large-scale batch extraction
  • Non-blocking document analysis
DO NOT USE Batch API
  • Pre-merge code review (devs are waiting)
  • Real-time customer chat
  • Interactive coding sessions
  • CI/CD pipeline steps blocking deployment
  • Any workflow with SLA under ~48h

Key Facts (Memorize These)

Cost savings50% vs real-time — NOT 90% (that's prompt caching)
Processing timeUp to 24 hours — no guaranteed latency SLA
Result orderResults come back OUT of order — always use custom_id to correlate
Failure recoveryResubmit ONLY failed items using their custom_id
Multi-turn tool callingNOT supported — each request is single-turn
Max requests per batch100,000 requests OR 256 MB per batch

Cost Comparison (Know All Three)

MethodRelative CostUse for
Real-time API1.0x (baseline)Interactive, latency-sensitive
Batch API0.5x (50% savings)Latency-tolerant bulk work
Prompt cache reads0.1x (90% savings)Repeated context across many calls

SLA Formula

Can you use Batch? → max_submission_interval = SLA_hours - 24h

  • 48h SLA → submit every 24h ✓
  • 30h SLA → submit every 6h ✓
  • 4h SLA → DO NOT USE BATCH (4 - 24 = negative)

Failure Recovery Pattern

Wrong

Resubmit the entire original batch — wastes cost on requests that already succeeded.

Correct

Parse results for failed custom_ids → resubmit ONLY those specific requests. If a document exceeded context limit, split it into chunks before resubmitting.

Exam Trap Table — 4.5

TrapCorrect Pattern

Use Batch for pre-merge CI checksCI checks are blocking — use real-time API
Results come back in submission orderResults are OUT of order — always correlate via custom_id
Resubmit entire batch on partial failureResubmit ONLY failed items — wastes cost otherwise
priority: critical flag to expediteThis field does not exist in the Batch API

5 Retry-with-Error-Feedback (4.3 / 4.6)

When schema-valid extraction fails semantic validation, the retry prompt must include three things: the original document, the failed extraction, and the specific validation errors. Without all three, the model gets no new signal.

What to Include in the Retry Prompt

Blind Retry (Wrong)

Re-send the original prompt unchanged. The model has no new information — same mistake is likely or a different random mistake occurs. Does not converge.

Retry-with-Feedback (Correct)
ORIGINAL DOCUMENT:
[the source text]

PREVIOUS (INCORRECT) EXTRACTION:
{"revenue_q1": 1200000, "total_h1": 2100000, "conflict_detected": false}

VALIDATION ERRORS TO FIX:
- total_h1 mismatch: Q1 + Q2 = 2,050,000 but total_h1 is 2,100,000
- conflict_detected should be True but is False

Please provide a corrected extraction that resolves these errors.

Retry Limits

SituationAction
Retryable: Info EXISTS in source, was extracted wrongRetry with error feedback — model can fix it
Non-retryable: Info does NOT exist in source at allAccept null/unclear — retrying will cause fabrication
Fabrication Risk

If you retry when the data is simply absent, the model may start fabricating a schema-valid value to "help" — now you have wrong data that looks correct. Nullable fields in your schema let the model honestly return null instead.

detected_pattern Field

Add a detected_pattern field to your extraction schema. When the model encounters difficulty, it describes what made extraction hard:

  • "totals stated without itemized breakdown"
  • "ambiguous currency (both USD and EUR mentioned)"
  • "Q4 figures missing, only YTD available"

Analyze these across dismissed/false-positive findings to find systematic prompt weaknesses → targeted fix instead of guesswork.

Self-Review Bias (4.6)

ProblemSame session reviews its own output → retains generation reasoning → defends its own decisions
FixIndependent fresh instance (separate invocation, no context from generation)
Doesn't fix itExtended thinking in the same session — still shares the same generation context

Exam Trap Table — 4.3/4.6

TrapCorrect Pattern
Blind retry (same prompt) fixes extraction errorsNo new information = no improvement. Include doc + failed extraction + specific errors.
Loosen schema to fix semantic errorsSemantic errors propagate silently — add application-layer validation instead
Retry fixes absent dataIf data isn't in the source, retry causes fabrication. Accept null and route to human review.
Ask Claude to explain its mistakes in natural language, then parseInclude specific machine-readable validation errors in the retry prompt

Question 1 of 12
A classification system has high false positive rates in one category. What is the correct fix?
A. Switch to a more capable model.
B. Add more unambiguous examples of every category.
C. Temporarily disable that category while improving its explicit criteria and contrastive examples.
D. Add a general instruction to "be more conservative."
Disabling the broken category preserves accuracy for others while you fix the root cause: the criteria and examples for that specific category. Uniform strictness reduction or vague instructions hurt accurate categories too.

Question 3 of 12
A JSON schema requires invoice_number as a string. The invoice document has no invoice number. What happens?
A. The model returns an error because a required field is missing.
B. The model fabricates a plausible-looking invoice number to satisfy the required field.

Question 4 of 12
The Batch API response for a 5-request batch comes back with results for requests 5, 2, 4, 1, 3. How should you match results to requests?
A. Sort results by timestamp to restore original order.
B. Match each result to its request using the custom_id field.
C. Batch results always come back in submission order — no special handling needed.
D. Use the batch's request_index field.
Batch results come back in any order. The custom_id you assign to each request is how you correlate results. There is no request_index or timestamp ordering guarantee.
Question 5 of 12
A structured extraction passes JSON schema validation but the stated total ($200) doesn't match the sum of line items ($147.48). What catches this error?
A. The JSON schema — it enforces semantic correctness.
B. Setting strict: true on the schema.
C. Application-layer semantic validation after extraction.
D. The conflict_detected field — the model always sets it correctly.
Schema validates syntax only. Cross-field consistency (totals matching) must be checked in application code. The conflict_detected field relies on the model setting it correctly — which is why you also need your own validation check.
Question 6 of 12

Batch API = 50% savings. Prompt cache reads = 90% savings. These are different mechanisms. The exam tests this confusion frequently.
Question 7 of 12

Question 8 of 12
An extraction returns null for a phone number field. When you retry with error feedback, the model fabricates a phone number. What went wrong?
A. The retry prompt didn't include the original document.
B. The phone number doesn't exist in the source document — this is a non-retryable situation.
C. The schema should have made phone a required field to prevent null.
D. Extended thinking would have found the phone number.
Retrying when data is absent causes fabrication. Null on a nullable field is correct behavior — the data isn't there. Only retry when information EXISTS in the source but was extracted incorrectly.
Question 9 of 12
You have 3 document extraction tools (invoice, receipt, contract). The document type is unknown. What tool_choice lets the model pick the right schema?
A. {"type": "tool", "name": "invoice"} — default to most common type.
B. "any" — model must call a tool and will pick the most appropriate one.
C. "auto" — model will figure out the right schema.
D. Call all 3 tools and pick the best result.
"any" is the right choice when you have multiple valid tools and want the model to pick. "auto" might return text instead of calling any tool. Forced selection requires knowing the type in advance.
Question 10 of 12
A batch of 1,000 extraction requests completes with 50 failures. What is the correct recovery?
A. Resubmit the entire original batch of 1,000 requests.
B. Switch the 50 failed items to the real-time API to restore the 50% batch discount.
C. Identify the 50 failed custom_ids and resubmit only those requests.
D. Discard the 50 failed items and proceed with the 950 successes.
Resubmit only failed items identified by custom_id. Resubmitting all 1,000 wastes the cost of 950 successful requests. Discarding failures creates coverage gaps.
