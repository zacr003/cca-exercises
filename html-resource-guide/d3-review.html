1 CLAUDE.md Configuration Hierarchy (3.1)

CLAUDE.md files stack like layers — they are concatenated, not overridden. All discovered files are merged into one combined instruction set. More specific scope wins when rules conflict across scopes.

The Three Scopes

LayerPathWho it's forShared via git?
User~/.claude/CLAUDE.mdPersonal preferences, machine-localNo — machine local
Project.claude/CLAUDE.md or ./CLAUDE.mdTeam-wide standardsYes — committed
Directory./subdirectory/CLAUDE.mdArea-specific contextYes — committed

@import and .claude/rules/

Correct Pattern — Modular via @import

When CLAUDE.md grows past 200 lines, split into topic-specific files in .claude/rules/ and import them. @import is for explicitly pulling in shared rule files.

# .claude/CLAUDE.md (hub file)
@import .claude/rules/testing.md
@import .claude/rules/api-conventions.md
@import .claude/rules/deployment.md

Subdirectory CLAUDE.md files do not require @import — they are auto-discovered when Claude Code works in that directory.

Conflict Resolution

Cross-scope conflictMore specific wins: directory > project > user
Same-scope conflictClaude picks arbitrarily — eliminate them at source
Load timingRe-read fresh each session — not cached
Size targetUnder 200 lines — split into .claude/rules/ with @import
Diagnose loaded filesRun /memory in Claude Code

2 Skills and Slash Commands (3.2)

CLAUDE.md = always-loaded universal standards. Rules that always apply belong here.
Skills / Commands = on-demand workflows. Invoked explicitly when you type /command.

Three Ways to Give Claude Instructions

MechanismWhen it activatesScopeUse for
CLAUDE.md / rulesAlways, automaticallyProject or userUniversal standards (always-on)
Slash commandsWhen you type /commandProject or userQuick team workflows
SkillsWhen you type /skill-nameProject or userComplex isolated tasks

Slash Commands

Project-Scoped (Shared)

Create .claude/commands/review.md — becomes /review for the whole team. Version-controlled.

User-Scoped (Personal)

Create ~/.claude/commands/standup.md — only available on your machine. Never shared via git pull.

SKILL.md Frontmatter Fields (know all three cold)

---

allowed-tools:         # restrict which tools the skill can call
  - Read
  - Grep
  - Glob
argument-hint: "Path to the module to analyze"   # prompts for input when invoked without args
---
FieldWhat it doesWhen to use

3 Path-Scoped Rules (3.3)

Files in .claude/rules/ with YAML paths: frontmatter load only when Claude Code edits a matching file — regardless of which directory it's in. This solves the problem that directory CLAUDE.md files can't reach files in other directories.

The Problem They Solve

Test files scattered across a codebase (Button.test.tsx next to Button.tsx, api.test.ts next to api.ts) — a directory CLAUDE.md in /components/ won't help a test file in /services/.

Frontmatter Syntax

---
paths:
  - "**/*.test.py"
  - "**/*.spec.py"
  - "**/test_*.py"
---
# Test File Conventions

- Every test function must start with `test_`
- Use pytest fixtures for shared setup — never duplicate setup code
- Never make real API calls in tests — mock all external services
Frontmatter Key

The key is paths: — NOT projects:, NOT directories:, NOT files:

Path-Scoped Rules vs. Directory CLAUDE.md

SituationRight choiceWhy
Test files scattered across many directories.claude/rules/testing.md with **/*.test.*Can't reach files across directories with directory CLAUDE.md
Conventions only for the backend/ directorybackend/CLAUDE.mdNaturally bounded by directory
Terraform conventions in /infra/, /deploy/, /modules/.claude/rules/terraform.md with **/*.tfFiles span multiple directories
API endpoint conventions for src/api/ onlysrc/api/CLAUDE.mdClear directory boundary
All Python files regardless of location.claude/rules/python.md with **/*.pyCross-cutting by file type

Key Behaviors

Rules without paths:Load at launch alongside CLAUDE.md — same as project-level
Rules with paths:Conditional — load only when editing a matching file
Override behaviorNone — all matching sources are concatenated, not overridden
Token benefitOnly loads when relevant — saves tokens when working in unrelated areas
DiagnoseRun /memory to see which rules files are currently loaded

Exam Trap Table — 3.3

TrapCorrect Pattern

projects: as the frontmatter keyThe correct key is paths:

4 Plan Mode vs. Direct Execution (3.4)

Plan mode = Claude explores and designs but does not modify source files. It can read files, run shell commands, and write a plan — but makes zero code changes until you switch to execution mode.

Architect first, then contractor. For trivial changes, call the contractor directly.

The Decision Framework

Use Plan ModeUse Direct Execution
Refactoring across 20+ filesFixing a single bug with a clear stack trace
Migrating from REST to GraphQLAdding one input validation check
Multiple valid approaches — need to compareChange where scope and approach are obvious
Unknown dependencies across the codebaseSingle-file modification with clear requirement
New authentication systemFixing a typo in an error message
Security-sensitive multi-component changeUpdating a config value

Quick test: "Do I know exactly what to change and where?" → Direct execution. "Do I need to explore first?" → Plan mode.

The Iterative Refinement Pattern

Wrong Mental Model

1. Activate plan mode → 2. Get plan → 3. Execute. This is one-shot oracle thinking.

Correct Mental Model

1. Activate plan mode → 2. Get plan → 3. Give feedback ("this doesn't account for X") → 4. Revised plan → 5. More feedback if needed → 6. Execute once plan is satisfactory.

The back-and-forth before any code changes is the value. Starting execution and realizing you need to rethink = costly rework.

Critical Exam Trap

Plan mode does not pause mid-execution at specific steps. Plan mode = safe exploration BEFORE execution. For mid-execution gating, use a PreToolUse hook instead.

Explore Subagent

Reading 30 files fills your main conversation context. The Explore subagent handles verbose discovery in a sub-agent and returns only a concise summary to the main session — keeping context clean.

Same principle as context: fork for skills: isolate verbose output from the session doing real work.

Exam Trap Table — 3.4

TrapCorrect Pattern

5 CI/CD and Headless Mode (3.6)

Without -p, Claude Code waits for interactive input. In CI, there is no human — the pipeline hangs indefinitely. The -p flag is the only way to use Claude Code in automated pipelines.

Flags and What They Do

FlagWhat it doesWhen to use
-p / --printNon-interactive mode — runs prompt, prints result, exitsRequired for all CI/CD pipelines
--output-format jsonWraps response in structured JSON envelopeWhen pipeline needs to parse the output
--bareSkips ALL auto-discovery: hooks, skills, MCP, CLAUDE.mdReproducible isolated CI execution
--append-system-promptAppends text to system prompt for that invocation onlyEphemeral per-run instructions

Settings Precedence (highest → lowest)

1. .claude/settings.local.jsonLocal overrides — usually gitignored
2. .claude/settings.jsonProject settings — version-controlled
3. ~/.claude/settings.jsonUser settings

--bare vs Default

Without --bare (default)
  • Loads CLAUDE.md files
  • Discovers and runs hooks
  • Loads skills from .claude/skills/
  • Connects MCP servers
  • Applies all local configuration
With --bare
  • Skips CLAUDE.md files
  • Skips hooks
  • Skips skills and plugins
  • Skips MCP server connections
  • Sets CLAUDE_CODE_SIMPLE env var
  • Clean, reproducible execution
Docker Trap

"Docker containers automatically isolate Claude Code config" — WRONG. Docker still auto-discovers config inside the container. Use --bare explicitly for stripped execution.

Independent Review Instance

Wrong — Same Session
claude -p "Generate tests"
# (same session) "Now review the tests you just wrote"
# → Self-review bias: generator and reviewer share reasoning context
Correct — Independent Instance
claude -p "Generate tests" > tests.py
claude -p "Review these tests" < tests.py   # fresh invocation
# → Reviewer has NO context from generation; catches issues generator rationalized away

CLAUDE.md for CI

CI-invoked Claude Code reads the same project CLAUDE.md as interactive use. Document testing standards, fixtures, and review criteria in CLAUDE.md — your CI review automatically follows the same quality bar as interactive development.

R Iterative Refinement Patterns (3.5)

When detailed instructions produce inconsistent results, the fix is concrete examples — not stronger instructions. This applies beyond classification: any time Claude misinterprets a prose description, 2–3 input/output examples resolve it faster than rewording.

When Examples Beat Instructions

SymptomWrong fixCorrect fix
Inconsistent interpretation of prose descriptionAdd more detail to the instructionProvide 2–3 concrete input/output examples
Classification keeps hitting edge casesLonger, more detailed criteriaContrastive adjacent examples showing the boundary
Model not following format correctlyRepeat the format instruction more firmlyShow exact before/after examples of correct format

Four Refinement Patterns

Interview patternAsk Claude to question YOU about requirements before proposing a design — surfaces ambiguity before implementation
Test-driven iterationWrite tests first, share test failures with Claude — model iterates against concrete pass/fail signal instead of vague prose feedback
Sequential for independent issuesFix bugs one at a time when they don't interact — each fix is clean and reviewable
Bundled for interacting issuesFix multiple issues in one message when they touch the same code — avoids conflicts between separate edits

Exam Trap Table — 3.5

TrapCorrect Pattern
Add more detailed instructions when current instructions are failingSwitch to concrete examples — instructions hit a ceiling; examples teach the boundary
Fix all issues in one big refactor messageSequential for independent issues; bundled only when issues interact
Provide design spec and ask Claude to build itInterview pattern — let Claude surface ambiguity first, then design together
Describe expected output in proseShow it — concrete before/after examples are unambiguous
T Built-in Tools and Claude Code Commands

Claude Code exposes built-in tools it uses when executing tasks. The exam tests which tool to use for which job, and when to fall back. Always prefer dedicated tools over Bash equivalents.

Built-in Tool Reference

ToolWhat it doesKey rule
GlobFind files by name pattern (e.g. **/*.py, src/**/*.ts)Use when you know the file pattern but not the content
GrepFind files/lines by content (ripgrep regex)Use when searching for a string, symbol, or pattern inside files
ReadRead file contents (with optional line range)Always Read before Edit — required to know current state
EditExact string replacement in a fileRequires unique match — fallback: Read + modify + Write
WriteCreate or completely overwrite a fileUse for new files or full rewrites; prefer Edit for partial changes
BashRun shell commandsUse ONLY when no dedicated tool exists — last resort
TaskSpawn a subagent with its own tool setMust be in allowedTools for coordinator to use it
WebFetchFetch content from a specific URLUse when you have the exact URL
WebSearchSearch the web by queryUse when you need to find a URL first

Glob vs. Grep — The Most-Tested Distinction

Glob — Find by File Name/Path
Glob("**/*.test.py")
→ finds all .test.py files

Glob("src/**/*.ts")
→ finds all .ts files under src/

Use when you know WHAT the file is called, not what's inside it

Grep — Find by Content
Grep("def verify_customer", "*.py")
→ finds files containing that function

Grep("isError", glob="**/*.json")
→ finds JSON files with isError

Use when you know WHAT'S INSIDE the file, not its name
